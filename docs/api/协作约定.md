# 上下层协作约定

本文记录下层（运行平台）与上层（前端/后端）在联调与并行开发中的接入方式和约定。

## 1. 联调接入

- 控制面仅监听 `127.0.0.1:18090`（代码强制 loopback），不直接对外。
- 同事接入两种方式：
  1. **SSH 反向隧道（推荐）**：`ssh -R 18090:127.0.0.1:18090 同事@她的机器IP`，前置是你已 `./run.sh tunnel`。
  2. **局域网转发**：`socat TCP-LISTEN:18090,fork,reuseaddr,bind=<Mac局域网IP> TCP:127.0.0.1:18090`。
- 鉴权两种方式：
  1. **BFF 后端转发登录 Cookie（推荐）**：她的后端登录后持有 Cookie，转发业务请求时透传。
  2. **前端 dev server 代理**：把 `/api` 代理到控制面，同源通信，避免 CORS。
- 账号隔离：给同事单独账号（再跑一次 `./run.sh configure-user`）。每用户独立实例与数据盘，互不影响。
- 已知限制：无 CORS 头；明文 HTTP；仅限内网/隧道联调，不暴露公网。

## 2. 接口变更分级与通知

| 变更类型 | 例子 | 对同事影响 | 是否需提前通知 |
|---|---|---|---|
| 内部实现优化 | 预热池、缓存、自动快照策略 | 接口无变化 | 否 |
| 新增接口 / 新增可选字段 / 新增错误码 | 新增 suspend/resume | 向后兼容 | 告知即可 |
| 状态枚举扩展 | 新增 suspended 状态 | 兼容，但她需能处理 | 提前说 |
| 破坏性变更 | 改字段名 / 删字段 / 改语义 / 改错误码 | 会报错 | 必须，且版本化 |

## 3. 影响控制原则

1. 能内部化的改动，不动接口。
2. 新能力只「增」接口/字段，不「删改」旧的。
3. 枚举扩展提前知会。
4. 破坏性变更升版本 + 提前通知。
5. 避免随意重启控制面（会中断她的 SSE 与进行中请求）。

## 4. 变更流程

改接口 → 先改 `docs/api/openapi.yaml` 与 `docs/api/API契约.md` → 通知同事 → 再部署。

## 5. 快照与预热对接口的影响

- 快照：已有 `POST /api/instances/{id}/suspend`、`/resume` 与 `suspended` 状态。自动快照策略属内部行为，不新增接口；唯一需同事知晓的是状态枚举扩展。
- 预热启动：纯内部优化，对外仍是 `POST .../messages`，接口零变化。若需运维管理接口，面向管理员而非业务接口。
