## 1.1 重要技术

### KVM

KVM 没有一个可以 `cd` 进入的项目目录。它是 Linux 内核中的虚拟化功能，主要通过下面的设备文件对用户态程序提供接口：

```
/dev/kvm
```

查看它：

```bash
ls -l /dev/kvm
```

### Firecracker

Firecracker 主程序位于：

```bash
/usr/local/bin/firecracker
```

确认位置：

```bash
command -v firecracker
```

实例启动后，Jailer 隔离环境中还会出现一个 Firecracker 可执行文件：

```bash
/srv/jailer/firecracker/<实例ID>/root/firecracker
```

### Jailer

Jailer 主程序位于：

```
/usr/local/bin/jailer
```

确认位置：

```bash
command -v jailer
```

它创建的实例隔离目录位于：

```bash
/srv/jailer/firecracker
```

## 1.2 系统盘与数据盘

`/srv/fc/artifacts` 保存多个 microVM 可以复用的 Guest 内核、只读系统盘、构建标识和软件包清单。

`/srv/fc/volumes/users` 保存用户独立使用的可写数据盘。当前每名用户绑定一块稳定数据盘，盘内可以包含多个 Workspace 和 Pi Session；数据盘不再按每次启动分配。

这些 `.ext4` 文件在宿主机上是磁盘镜像文件。冷启动时，Firecracker 将系统盘呈现为 Guest 第一块虚拟磁盘 `/dev/vda`，将用户数据盘呈现为第二块虚拟磁盘 `/dev/vdb`。

**查看 Firecracker 磁盘访问模式**

在 Ubuntu Host 中读取运行实例的配置，例如：

```bash
sudo python3 -m json.tool /srv/jailer/firecracker/cli-demo/root/config.json
```

当前配置中的磁盘部分为：

```json
"drives": [
  {
    "drive_id": "rootfs",
    "path_on_host": "/rootfs.ext4",
    "is_root_device": true,
    "is_read_only": true
  },
  {
    "drive_id": "data",
    "path_on_host": "/data.ext4",
    "is_root_device": false,
    "is_read_only": false
  }
]
```

`path_on_host` 是 Firecracker 在 Jailer chroot 中看到的路径；`is_read_only` 控制虚拟磁盘的写入能力，和文件的 UID、GID、普通权限是不同层面的限制。

`config.json` 由冷启动流程生成。快照恢复使用 API Socket 加载已保存状态，不要求重新生成这份冷启动配置。

### 1.2.1 系统盘

系统盘、Guest Linux 内核及相关构建文件保存在 `/srv/fc/artifacts` 目录中。

下面是开发环境曾经生成的目录示例；文件时间、inode、链接数和旧版内核是否保留会随环境变化：

```bash
agentdev@agent-platform-dev:/srv/fc/artifacts$ ls -lh
total 896M
-rw-r--r-- 1 root root   65 Oct 19 06:22 agent-rootfs.build-id
-rw-r--r-- 2 root root 4.0G Oct 19 06:22 agent-rootfs.ext4
-rw-r--r-- 1 root root 3.7K Oct 19 06:22 agent-rootfs.manifest
-rw-r--r-- 1 root root 1.9M Oct  7 01:47 initramfs.cpio
-rw-r--r-- 2 root root  17M Oct  7 01:54 vmlinux-5.10.268
-rw-r--r-- 1 root root  18M Oct  7 01:47 vmlinux-6.1.186
```

这些文件的用途分别为：

- `agent-rootfs.ext4`：Pi Runtime 使用的 Ubuntu 根文件系统。
- `agent-rootfs.build-id`：用于判断系统盘的构建输入是否发生变化。
- `agent-rootfs.manifest`：记录由 `dpkg` 管理的 Ubuntu 软件包及版本。
- `initramfs.cpio`：最小启动测试使用的 initramfs 归档。
- `vmlinux-5.10.268`：当前 Pi Runtime microVM 使用的 Guest Linux 内核。
- `vmlinux-6.1.186`：历史下载残留，不是当前受管实例要求的启动资产。

#### `vmlinux-5.10.268`

```bash
agentdev@agent-platform-dev:/srv/fc/artifacts$ file vmlinux-5.10.268
vmlinux-5.10.268: Linux kernel ARM64 boot executable Image, little-endian, 4K pages
```

上述 ARM64 输出来自 Apple Silicon 开发环境。构建脚本会根据 Host 的 `aarch64` 或 `x86_64` 架构选择对应内核和软件包；不能将 ARM64 内核用于 x86_64 Guest。

> 只负责 Linux 内核运行，例如管理 CPU、内存、磁盘和进程。

Linux内核 + Ubuntu根文件系统，两者组合起来才构成可以运行的 Guest 系统

> Firecracker 不需要像普通虚拟机一样从 ISO 启动安装程序，而是直接加载指定的 Guest Linux 内核和根文件系统，因此启动路径更短。

#### `agent-rootfs.ext4`

`agent-rootfs.ext4` 是 microVM 使用的 Ubuntu 系统盘镜像，也就是 Guest Linux 的根文件系统。

它与普通 Ubuntu 安装盘 ISO 不同。ISO 用于安装操作系统，而 `agent-rootfs.ext4` 已经包含能够直接运行的 Linux 目录、基础命令、Node.js、Pi Agent 和 Guest 启动脚本。Firecracker 可以直接使用它启动 microVM。

> `agent-rootfs.ext4` 由 Ubuntu 宿主机上的构建脚本离线生成，构建过程不启动 microVM，也不执行 Guest 内核。
>
> `./run.sh start` 会同步代码、准备内核并调用 rootfs 构建入口。构建脚本先计算输入指纹，再决定复用、离线刷新 Guest 项目文件，或者完整重建。Control Plane 为用户启动每一台 microVM 时只读取已准备的镜像，不会重新执行 debootstrap。

系统盘中的主要目录包括：

```
/etc          Guest Linux 的系统配置
/usr          Linux 命令和程序文件
/usr/local    Node.js、Pi Agent 和 Guest 启动脚本
/home/pi      Pi 用户的主目录
/workspace    数据盘工作区的挂载入口
/mnt          数据盘的初始挂载位置
/var          Guest Linux 的运行数据目录
/dev          Guest 启动后动态生成的设备入口
/proc         Guest 启动后动态生成的进程和内核信息
/sys          Guest 启动后动态生成的内核设备信息
```

Firecracker 启动 microVM 时，会将 `agent-rootfs.ext4` 注册为 Guest 的第一块虚拟磁盘：

```
agent-rootfs.ext4 → /dev/vda
```

因为它是根设备，所以 Guest Linux 会把它作为 `/` 根文件系统使用。

当前受管实例采用系统盘只读、用户数据盘可写的双盘结构：

```
/dev/vda    系统盘    只读
/dev/vdb    数据盘    可写
```

系统盘中的 `/workspace` 只是数据盘工作区的挂载入口。microVM 启动后，数据盘中的 `workspace` 目录会显示在 `/workspace`，Pi Agent 创建的用户文件不会直接写入只读系统盘。

在宿主机中，`agent-rootfs.ext4` 是一个文件，而不是普通目录，因此不能直接使用 `cd` 进入。可以使用 `debugfs` 读取它内部的 ext4 文件系统。

查看系统盘根目录：

```bash
sudo debugfs -R 'ls -l /' /srv/fc/artifacts/agent-rootfs.ext4
```

#### `agent-rootfs.build-id`

文件内容是一串 SHA-256 构建指纹，用于判断现有系统盘是否对应当前构建输入。它不是对 4 GiB 镜像全文计算得到的文件校验和。

当前指纹的输入为：

```text
Host CPU 架构
config/versions.env
scripts/linux/build-agent-rootfs.sh
scripts/guest/agent-init.sh
scripts/guest/pi-rpc-session.sh
```

`scripts/linux/build-agent-rootfs.sh` 根据这些输入计算新 Build ID，并与 `/srv/fc/artifacts/agent-rootfs.build-id` 比较。

指纹一致且必要产物存在时，脚本检查 ext4 是否干净并复用镜像。指纹变化时，如果 Ubuntu、Node、Pi、UID 和架构等基础版本仍匹配、镜像链接数为 1 且具备 socat，脚本可离线更新 Guest 项目文件；不满足条件时执行完整构建。

```text
计算构建指纹
    ↓
相同 → 检查文件系统 → 复用 rootfs
不同 → 满足离线刷新条件 → 更新 Guest 脚本与构建元数据
     → 不满足条件       → 完整构建
```

构建结果同时写入 Guest 的 `/etc/ai-agent-platform-build`，保存 Node/Pi 版本、UID、架构和静态安全验证标志。正式 Guest 启动读取这些元数据；`runtime-smoke-test` 才再次执行真实版本命令。

已有实例可能通过硬链接继续使用旧 inode。更新通用镜像不会自动替换正在运行实例中的系统盘；Guest 文件更新后需要重新启动实例。

#### `agent-rootfs.manifest`

`agent-rootfs.manifest` 是构建系统盘时通过 `dpkg-query` 生成的软件包清单，记录 Ubuntu 软件包名称及其版本。

它只记录由 `dpkg` 管理的软件包。手动解压安装的 Node.js，以及通过 npm 安装的 Pi Agent，不一定出现在该文件中。

使用以下命令查看：

```
less /srv/fc/artifacts/agent-rootfs.manifest
```

按 `q` 可以退出 `less`。

### 1.2.2 数据盘

当前正式用户数据盘保存在：

```text
/srv/fc/volumes/users/<user-id>.ext4
```

用户 ID 与磁盘路径由 `UserVolumeStore` 保存在 `/var/lib/fc/control-plane.db` 的 `user_volumes` 表中。实例 ID 与用户 ID 是两个标识，不能根据实例名直接推断用户磁盘文件名。

数据盘默认逻辑容量为 1 GiB，首次启动时创建，后续复用。它是稀疏镜像，`ls -lh` 显示逻辑大小，`du -h` 显示实际占用，两者可能不同。

#### `users`

`/srv/fc/volumes/users` 是当前受管用户卷目录。每个用户绑定一块稳定数据盘，停止或回收 microVM 后继续保留。

#### `instances`

`/srv/fc/volumes/instances` 是旧版按实例保存数据盘的兼容目录。升级时 `InstanceRuntime.adopt_legacy_volume()` 可将用户原有实例盘迁移到用户卷路径。新文档和新部署以 `users` 为准。

#### `smoke`

`/srv/fc/volumes/smoke` 等目录可能由独立 smoke test 创建。测试脚本也可以指定自己的临时卷目录；这些数据不代表正式用户卷。

旧版 `lab` 命令和脚本已经移除。旧机器上遗留的 lab 目录仅是历史文件，不属于当前启动链路。

##### 用户数据盘 `<user-id>.ext4`

数据盘内部主要包含：

```text
/
├── lost+found
├── workspace
│   └── workspaces
│       └── workspace-xxxxxxxxxxxxxxxx
└── pi-state
    └── agent
        ├── models.json
        └── sessions
            └── <Pi生成的目录>
                └── <时间等前缀>_conversation-xxxxxxxxxxxxxxxx.jsonl
```

`workspaces` 和 Session 文件会随实际使用创建。新磁盘还没有执行会话时，这些子目录可能不存在。

确认实例已经停止后，可以在 Ubuntu Host 只读查看镜像：

```bash
sudo debugfs -R 'ls -l /' '/srv/fc/volumes/users/<user-id>.ext4'
sudo debugfs -R 'ls -l /pi-state/agent/sessions' '/srv/fc/volumes/users/<user-id>.ext4'
```

上述 `<user-id>` 是占位符，执行前替换为真实用户 ID。运行中直接读取镜像可能看到 Guest 尚未刷盘的中间状态；不要用 `debugfs -w` 或宿主机可写挂载去修改正在被 Guest 使用的数据盘。

###### 关于所有者

宿主机数据盘通常采用：

```text
-rw------- firecracker firecracker <user-id>.ext4
```

这里的 `firecracker` 是 Host 上运行 VMM 的低权限系统账户，不是登录平台的业务用户。它需要读取和写入镜像后端。

Guest 内的文件权限由 Guest 自己的 UID/GID 管理。当前 Pi 用户为 `1001:1001`，工作区和 Pi 状态目录归该用户所有。Host 镜像文件的所有权与 Guest 内部目录的所有权是两层独立权限。

###### `lost+found`

ext4 自动创建的恢复目录。文件系统异常后，`fsck` 可将无法确定原路径的文件放入这里。正常情况下通常为空，不属于 Pi 工作目录。

###### `workspace`

保存用户文件、项目内容和任务产物，启动后 bind mount 到 Guest 的 `/workspace`。

通过当前 Workspace 创建的任务，其实际工作目录为：

```text
/workspace/workspaces/<workspace-id>
```

例如 Pi 在该工作区创建 `report.md`，数据盘内部位置为 `workspace/workspaces/<workspace-id>/report.md`。不同 Workspace 是同一块盘上的目录分组，不是多块磁盘，也不是独立安全沙箱。

###### `pi-state`

保存 Pi 的模型路由配置和原生 Session，启动后 bind mount 到：

```text
/home/pi/.pi
```

`agent/models.json` 保存模型名称、Host 网关 URL 和占位凭据。`agent/sessions` 保存 Pi 原生 JSONL Session，记录可用于恢复上下文的消息及 Pi 状态。

新会话使用原生 Session；只有没有平台 Session ID 的临时调试任务才使用 `--no-session`。Conversation 元数据和展示消息缓存保存在 Host SQLite，原生 Session 正文保存在用户数据盘。

真实 DeepSeek API Key 不写入用户数据盘。

### 1.2.3 Jailer 硬链接 / Guest 磁盘挂载

microVM 启动前，平台需要把 Guest 内核、系统盘和数据盘提供给 Firecracker。

 Jailer 会通过 `chroot` 限制 Firecracker 可以访问的文件范围。Firecracker 进入隔离环境后，无法继续使用 `/srv/fc` 中的原始路径，因此启动脚本会先把需要的文件硬链接到实例专属的 Jailer 目录。

#### 实例启动流程

microVM 启动分为三个阶段：

1. **镜像准备**：将操作系统、Node.js、Pi 和初始化脚本装入通用系统盘。
2. **实例准备**：确定本次实例的磁盘、CPU、内存和网络配置，生成 `config.json`。
3. **Guest 启动**：Jailer 建立隔离环境，Firecracker 创建虚拟机，Guest 完成磁盘挂载和服务初始化。

实例配置由项目启动代码准备。Jailer 使用准备好的文件和参数，不负责选择实例地址、生成配置文件或构建系统镜像。

##### 1. 启动入口

当前有两个不同的“启动”操作。

在 macOS 项目目录执行 `./run.sh start`，入口读取 `.env`，通过 rsync 同步项目，再经 SSH 调用 Ubuntu Host 中的准备和服务脚本：

```text
run.sh start
    ↓
scripts/linux/prepare-microvm-smoke.sh
    ↓
scripts/linux/build-agent-rootfs.sh
    ↓
scripts/linux/control-plane-service.sh start
```

这一步准备共享资产并启动 Control Plane，不会立即为用户创建 microVM。

用户随后通过 `./agentctl start cli-demo` 显式启动，或者在 `./agentctl chat` 中发送消息，由 Control Plane 按需启动已经停止的用户实例：

```text
agentctl → HTTP请求
    ↓
services/control-plane/server.py
    ↓
ControlPlane.start()
    ↓
services/instance-manager/runtime.py
    ↓
InstanceRuntime.start(instance_id, owner_id)
```

直接在 Ubuntu Host 部署时，使用 `./run-linux.sh start` 准备资产和启动控制面，不经过 macOS 的 SSH 同步入口。

##### 2. 系统镜像准备

`scripts/linux/build-agent-rootfs.sh` 构建或更新通用系统盘：

```text
/srv/fc/artifacts/agent-rootfs.ext4
```

主要项目文件对应关系为：

| 仓库源码 | Guest 安装位置 | 作用 |
|---|---|---|
| `scripts/guest/agent-init.sh` | `/usr/local/sbin/agent-init` | 初始化挂载、网络和 RPC 监听 |
| `scripts/guest/pi-rpc-session.sh` | `/usr/local/sbin/pi-rpc-session` | 选择工作区和 Session，启动本次 Pi |
| Ubuntu 包管理器安装的 socat | `/usr/bin/socat` | TCP 与标准输入输出桥接 |

旧 `agent-task-worker`、`pi-event-forwarder.mjs` 和 `workspace-operation.mjs` 已从正式镜像安装逻辑中移除。

rootfs 保存通用程序和目录。IP、TAP、用户盘、模型网关地址等每实例参数，由 Host 启动模块在运行时提供。修改 IP、vCPU 或内存无需因此重新安装 Pi。

##### 3. 实例资源准备

当前流程由 `InstanceRuntime.start()` 组织：

```text
检查 Host 权限、二进制与共享镜像
    ↓
按 owner_id 查找或创建用户数据盘
    ↓
e2fsck 检查数据盘
    ↓
NetworkManager.allocate() 预留网络
    ↓
configure_agent_volume() 写入 Pi 模型路由
    ↓
NetworkManager.setup() 创建 TAP 与 nftables
    ↓
start_model_gateway() 启动 Host 模型网关
    ↓
prepare_jail() 准备硬链接和 config.json
    ↓
启动 Jailer → Firecracker → Guest
    ↓
确认 Guest 就绪，激活租约并登记生命周期
```

这些大多是 Python 类中的方法，不是各自独立运行的后台服务。

###### 网络准备

`runtime.py` 直接导入 `services/instance-manager/network_manager.py`，创建：

```python
NetworkManager(
    SQLiteLeaseStore(self.state_database),
    allow_host_connections=True,
)
```

启动过程中调用：

```python
network = self.network_manager.allocate(instance_id)
self.network_manager.setup(network, uid, (GATEWAY_PORT,))
```

`GATEWAY_PORT` 当前为 `18082`。返回的 `network` 字典包含 `subnet`、`host_ip`、`guest_ip`、`guest_mac`、`tap`、`nft_table` 等字段；该字典继续用于模型配置、网关监听、Firecracker 配置和生命周期登记。

正式租约写入 `/var/lib/fc/control-plane.db` 的 `network_leases`。旧 `lab_network.py` 不属于当前仓库运行链路。

###### 数据盘配置

`configure_agent_volume(volume_path, host_ip)` 在 Guest 启动前，将用户 ext4 镜像临时挂载到 Host 的 `/var/tmp/agent-volume-config.*`，写入：

```text
pi-state/agent/models.json
```

其中保存 `http://<host_ip>:18082/v1`、模型名和 `gateway-placeholder`，随后同步并卸载。

Host 的这次离线挂载与 Guest 后续挂载是两个阶段。数据盘不能同时由 Host 和运行中的 Guest 以可写文件系统方式使用。

###### 宿主机服务

`start_model_gateway()` 启动 `services/tool-gateway/gateway.py`，监听本实例的 Host TAP 地址和 `18082` 端口。

真实 API Key 来自 Host 凭据文件，复制到实例 sidecars 目录并设为网关账户只读。网关进程在 Host 运行，不打包进 Guest rootfs。

```text

    ↓

    ↓

agent-init 挂载用户数据盘、配置 eth0、启动 socat

Host TAP 在配置生成前已经存在；Guest eth0 的 IP 和路由在 Guest 初始化时设置。

##### 5. Jailer 与 Firecracker

`InstanceRuntime.start()` 使用 `subprocess.Popen()` 启动 Jailer。等价参数形式为：

```bash
/usr/local/bin/jailer \
  --id cli-demo \
  --exec-file /usr/local/bin/firecracker \
  --uid <firecracker-uid> \
  --gid <firecracker-gid> \
  --chroot-base-dir /srv/jailer \
  --cgroup-version 2 \
  --resource-limit no-file=2048 \
  -- \
  --api-sock /firecracker.socket \
  --config-file /config.json
```

UID/GID 由 Host 系统账户查询得到，示例中的占位符需要替换。单独的 `--` 前为 Jailer 参数，之后为 Firecracker 参数。

Jailer 依据可执行程序名和实例 ID，确定根目录 `/srv/jailer/firecracker/cli-demo/root`，设置隔离与低权限身份，再执行 Firecracker。Firecracker 从 chroot 内的 `/config.json` 读取配置，通过 `/dev/kvm` 创建和运行 Guest。

##### 6. Guest 初始化

Guest 内核根据 `root=/dev/vda ro rootfstype=ext4` 挂载系统盘，根据 `init=/usr/local/sbin/agent-init` 执行镜像内的脚本：

```text
挂载 /proc、/sys、/dev、/dev/pts
    ↓
将初始化日志重定向到 /dev/ttyS0
    ↓
读取 /proc/cmdline
    ↓
挂载 /run、/tmp 和 /dev/vdb
    ↓
bind mount workspace 与 pi-state
    ↓
配置 eth0、默认路由和 resolv.conf
    ↓
读取构建元数据，检查当前工作区写权限
    ↓
输出 AGENT_RUNTIME_READY
    ↓
以 pi 用户启动 socat，确认监听后输出 PI_RPC_READY
```

Node/Pi 版本和静态权限在 rootfs 构建时已验证；正常启动不再重复运行 Pi 版本命令。`PI_RPC_READY` 表示 TCP 监听器已就绪，客户端首次发送命令时才启动本次 Pi 进程。

##### 7. 两类控制通道

| 通道 | 使用者 | 作用 |
|---|---|---|
| Firecracker API Socket | Host `InstanceRuntime` | 控制 VMM 暂停、快照创建和恢复 |
| Guest TCP 8080 / JSONL | Host `PiGateway` | 发送 Agent 命令、接收执行事件 |

API Socket 是 Host 上的 Unix domain socket；Pi RPC 使用 Host 与 Guest 之间的 TCP。停止 VMM 与结束一次 Pi 对话是不同操作。

#### Jailer 实例目录

基础目录为 `/srv/jailer/firecracker`。每个实例使用：

```text
/srv/jailer/firecracker/<instance-id>/root
```

例如查看 `cli-demo`：

```bash
sudo -i
cd /srv/jailer/firecracker/cli-demo/root
ls -lh
exit
```

正常停止并清理后，这个目录会删除。仅看到目录存在不能证明 VMM 正在运行，应结合 `agentctl status` 和 PID 状态判断。

#### 准备 chroot 目录

当前源码位于 `services/instance-manager/runtime.py` 的 `prepare_jail()`，默认同步到 Ubuntu Host 的 `/opt/ai-agent-platform/services/instance-manager/runtime.py`。

核心逻辑为：

```python
shutil.rmtree(paths["jail"], ignore_errors=True)
paths["chroot"].mkdir(parents=True, mode=0o755)
os.link(self.kernel_source, paths["chroot"] / "vmlinux")
os.link(self.rootfs_source, paths["chroot"] / "rootfs.ext4")
os.link(paths["volume"], paths["chroot"] / "data.ext4")
config_path = paths["chroot"] / "config.json"
config_path.write_text(json.dumps(config, separators=(",", ":")) + "\n", encoding="utf-8")
os.chmod(config_path, 0o644)
```

这段代码清理旧 jail、创建新目录、建立三个硬链接，并写入配置。配置生成发生在调用 Jailer 之前，此处尚未执行 chroot。

`0755` 表示目录所有者可读写进入，组和其他用户可读、可进入。`0644` 表示配置文件所有者可读写，组和其他用户只读。父目录权限、VMM 身份和只读磁盘设置仍会进一步影响访问。

上述代码中的 `os.link()` 对应硬链接操作；旧 Bash 示例中的 `install`、`ln`、`<<EOF` 不再是当前受管实例的配置生成实现。

#### 启动前准备的三个核心文件

```text
/srv/fc/artifacts/vmlinux-5.10.268
    → /srv/jailer/firecracker/<instance-id>/root/vmlinux

/srv/fc/artifacts/agent-rootfs.ext4
    → /srv/jailer/firecracker/<instance-id>/root/rootfs.ext4

/srv/fc/volumes/users/<user-id>.ext4
    → /srv/jailer/firecracker/<instance-id>/root/data.ext4
```

硬链接为同一份 Host 文件建立多个目录项，不复制镜像内容。inode 保存文件元数据和数据块位置；同一文件系统内，两个路径的 inode 相同，表示它们访问同一份文件。

查看系统盘硬链接：

```bash
sudo ls -li /srv/fc/artifacts/agent-rootfs.ext4 /srv/jailer/firecracker/cli-demo/root/rootfs.ext4
```

链接数可能随着运行实例增减。删除一个 jail 内的链接，只删除该路径；只要原始路径仍存在，镜像内容就保留。

三个来源文件与 Jailer 必须支持同文件系统硬链接。跨文件系统无法直接使用当前方式准备 jail。

#### `config.json`

`config.json` 是 `prepare_jail()` 动态生成的普通 JSON 文件，不是原始磁盘的硬链接。冷启动命令通过 `--config-file /config.json` 将其交给 Firecracker。

```text
Host:
/srv/jailer/firecracker/<instance-id>/root/config.json

Firecracker chroot 内:
/config.json
```

`/rootfs.ext4`、`/data.ext4`、`/vmlinux` 也按同样的 chroot 路径规则解释。这些是 Firecracker 进程看到的 Host 文件路径，不是 Guest 内的 Linux 根目录。

正常停止删除 jail 后，配置一并清理；再次冷启动重新生成。快照恢复则启动空 VMM，通过 API Socket 加载快照状态。

#### 执行 chroot 并启动 Firecracker

Jailer 按以下规则计算目录：

```text
<chroot-base-dir>/<可执行程序名>/<实例ID>/root
```

当前对应 `/srv/jailer/firecracker/<instance-id>/root`。Jailer 调用 Linux 隔离机制，使 Firecracker 将此目录作为自身的 `/`，再以指定低权限 UID/GID 执行 VMM。

`--cgroup-version 2` 选择 cgroup v2 机制；该参数本身不代表已经配置 CPU 或内存的 cgroup 配额。`--resource-limit no-file=2048` 单独限制文件描述符数量。

Firecracker 自身使用 seccomp 约束系统调用；Jailer 配合 chroot、权限收缩等方式降低 Host 进程权限。Guest 的 2 vCPU、1024 MiB 则由 VMM 机器配置决定。

`--api-sock /firecracker.socket` 让 Firecracker 在 chroot 内创建 Unix API Socket，Host 使用完整 jail 路径访问；它不创建 TCP 监听端口。

#### Guest Linux 内核的加载过程

Guest Linux 内核最初是 Ubuntu 宿主机中的一个静态文件：

```
/srv/fc/artifacts/vmlinux-5.10.268
```

启动 microVM 前，项目脚本将它硬链接到实例的 Jailer 目录：

```
/srv/jailer/firecracker/<instance-id>/root/vmlinux
```

同时，项目脚本动态生成 `config.json`，在其中指定 Firecracker 应该加载哪个内核：

```bash
{
  "boot-source": {
    "kernel_image_path": "/vmlinux",
    "boot_args": "root=/dev/vda ro rootfstype=ext4 console=ttyS0 init=/usr/local/sbin/agent-init"
  }
}
```

这里的 `/vmlinux` 是 Firecracker 进入 Jailer 的 `chroot` 后看到的路径。它在 Ubuntu 宿主机上的完整路径实际是：

```
/srv/jailer/firecracker/<instance-id>/root/vmlinux
```

Firecracker 读取该内核镜像，把其中已经编译好的 ARM64 内核机器代码放入 microVM 的 Guest 内存，然后通过 KVM 启动虚拟 CPU，使虚拟 CPU 从内核入口开始执行。

完整过程为：

```
宿主机中的vmlinux内核文件
    ↓ 项目脚本建立硬链接
Jailer中的/vmlinux
    ↓ Firecracker读取并加载
microVM的Guest内存
    ↓ Firecracker通过KVM启动vCPU
Guest Linux内核开始运行
```

内核开始运行后，负责初始化 vCPU、内存和虚拟设备，并准备挂载根文件系统。

项目编写的 `agent-init`、`pi-rpc-session` 等脚本不属于 Linux 内核。这些脚本保存在系统盘中，必须等内核挂载系统盘后才能运行。

因此，这一阶段的职责关系是：

- 项目启动脚本：决定使用哪个内核，并生成 `config.json`。
- Jailer：限制 Firecracker 可以访问的文件范围。
- Firecracker：读取内核文件，并把内核加载到 Guest 内存。
- KVM：提供虚拟 CPU 的底层运行能力。
- Guest Linux内核：在虚拟 CPU 上实际执行。

`vmlinux` 加载后不会作为普通文件出现在 Guest 文件系统中。它已经成为正在运行的 Guest Linux 内核。

#### `ext4` 文件系统挂载

Firecracker microVM 的磁盘启动过程包含三个不同层面的操作：虚拟磁盘注册、文件系统挂载和 bind mount。磁盘从始至终都没有被转换成目录，目录只是 Linux 内核提供的文件系统访问方式。

虚拟磁盘注册由 Firecracker 完成：

```
rootfs.ext4 → Guest块设备/dev/vda
data.ext4   → Guest块设备/dev/vdb
```

这个阶段只让 Guest 识别到虚拟硬盘，磁盘中的目录还没有接入 Guest 的目录树。

文件系统挂载由 Guest Linux 内核完成：

```
/dev/vda → /
/dev/vdb → /mnt/agent-data
```

内核使用 ext4 驱动解析块设备中的文件系统，并把文件系统目录树接到指定的挂载点。这个操作称为文件系统挂载，而不是把磁盘转换成目录。

bind mount 同样由 Guest Linux 内核完成：

```
/mnt/agent-data/workspace → /workspace
/mnt/agent-data/pi-state  → /home/pi/.pi
```

bind mount 不再解析磁盘，而是把已经可以访问的目录绑定到另一个路径，使 Pi Agent 可以继续使用固定的工作目录和状态目录。

三类操作的区别如下：

| 操作         | 数据来源       | 执行者          | 结果                                   |
| ------------ | -------------- | --------------- | -------------------------------------- |
| 虚拟磁盘注册 | 宿主机磁盘镜像 | Firecracker     | Guest看到`/dev/vda`和`/dev/vdb`        |
| 文件系统挂载 | Guest块设备    | Guest Linux内核 | 文件系统通过`/`或`/mnt/agent-data`显示 |
| bind mount   | 已挂载的目录   | Guest Linux内核 | 同一目录通过另一个路径访问             |

一句话总结：

> Firecracker 将磁盘镜像呈现为 Guest 块设备，Guest Linux 内核再将块设备中的文件系统挂载到目录树，最后通过 bind mount 把数据盘子目录放到 Pi Agent 使用的固定路径。

#### 挂载后作为目录使用

目录是文件系统中的实际对象，以目录项、inode 等结构保存在磁盘上；Linux 内核将这些结构组织为程序可访问的目录树。

宿主机中的 `/srv/fc/volumes/users/<user-id>.ext4` 是一个普通文件，但它内部已经按照 ext4 格式保存了：

```
超级块
inode表
目录项
文件权限
文件内容
文件系统日志
```

Firecracker 将这个宿主机文件提供为 Guest 虚拟块设备 `/dev/vdb` 此时 Guest 只能识别到一块虚拟磁盘，数据盘中的目录还没有接入 Guest 的目录树。执行：

```bash
mount -t ext4 /dev/vdb /mnt/agent-data
```

后，Guest Linux 内核使用 ext4 驱动解析 `/dev/vdb` 中的文件系统结构，并通过 Linux Virtual File System 将其中的根目录接入：

```
/mnt/agent-data
```

挂载后显示为：

```
/mnt/agent-data
├── lost+found
├── workspace
└── pi-state
```

这个过程不是把磁盘转换成目录，也没有复制数据。数据盘仍然是 `/dev/vdb` 虚拟块设备，只是其中已有的 ext4 目录树通过 `/mnt/agent-data` 接入了 Guest 的统一目录树。

在 Guest Linux 中：

```
/mnt/agent-data/workspace
```

是真正的 ext4 目录。它具有自己的 inode、UID、GID、权限和目录项，可以正常执行：

```
cd /mnt/agent-data/workspace
ls
mkdir docs
touch test.txt
```

这些命令不会直接解析 ext4。Bash 和其他程序通过系统调用请求 Guest Linux 内核操作文件，内核的 VFS 负责解析路径，ext4 驱动负责读取和修改 `/dev/vdb` 中的文件系统数据。

例如执行：

```
cd /mnt/agent-data/workspace
```

路径解析过程为：

```
Guest根目录/
    ↓
进入系统盘中的/mnt
    ↓
到达/mnt/agent-data挂载点
    ↓
切换到数据盘/dev/vdb的ext4文件系统
    ↓
进入数据盘中的workspace目录
```

`mount` 本身通常也是一个用户态程序：

```
/usr/bin/mount
```

在 Bash 中执行 `mount` 时，实际过程是：

```
Bash启动mount程序
    ↓
mount程序向Guest内核发出挂载系统调用
    ↓
Guest内核使用ext4驱动解析/dev/vdb
    ↓
Guest内核在VFS挂载表中建立挂载关系
```

因此，同一个 `data.ext4` 在不同层面具有不同含义：

```
Ubuntu宿主机：普通文件
Firecracker：虚拟磁盘的后端存储
Guest Linux：包含真实目录和文件的ext4文件系统
```

可以总结为：

> ext4 镜像在宿主机上是普通文件，在 Guest 中通过 Firecracker 表现为虚拟块设备。Guest Linux 内核使用 ext4 驱动解析其中已有的文件系统结构，并通过 VFS 将目录树接入指定挂载点。因此，挂载后的路径在 Guest 中属于真正可以被 Bash 和应用程序操作的目录。

#### 系统盘的注册与挂载

系统盘原文件位于：

```
/srv/fc/artifacts/agent-rootfs.ext4
```

该文件内部已经包含完整的 Ubuntu 根文件系统，例如：

```
/etc
/usr
/usr/local
/home
/mnt
/var
```

系统盘构建过程中，项目已经在镜像内部创建了：

```
/mnt/agent-data
```

此时它只是系统盘中的一个空目录，作为后续挂载数据盘的入口。

启动 microVM 前，项目脚本将系统盘硬链接到 Jailer 目录：

```
/srv/jailer/firecracker/<instance-id>/root/rootfs.ext4
```

项目脚本生成的 `config.json` 中包含：

```bash
{
  "drive_id": "rootfs",
  "path_on_host": "/rootfs.ext4",
  "is_root_device": true,
  "is_read_only": true
}
```

这些字段分别表示：

- `path_on_host`：Firecracker 在 Jailer 中读取的系统盘路径。
- `is_root_device: true`：该磁盘是 Guest 的根设备。
- `is_read_only: true`：Guest 只能读取系统盘，不能修改它。

Firecracker 读取 Jailer 中的 `/rootfs.ext4`，并把它作为虚拟块设备提供给 Guest。当前配置下，Guest Linux 内核将它识别为：

```
/dev/vda
```

但是“注册为 `/dev/vda`”只表示 Guest 识别到了一块虚拟硬盘，系统盘内部目录此时还没有成为 Guest 的目录树。

项目还通过 `boot_args` 预设：

```
root=/dev/vda ro rootfstype=ext4
```

含义为：

- `root=/dev/vda`：使用 `/dev/vda` 作为根文件系统。
- `ro`：以只读方式挂载。
- `rootfstype=ext4`：按照 ext4 文件系统解析。

> `boot_args` 的具体内容是由项目启动脚本预设的，不是 Linux 内核自动生成的。可以在 `config.json` 里找到

Guest Linux 内核启动后，根据这些参数解析 `/dev/vda` 中的 ext4 文件系统，并将其挂载为 Guest 的根目录：

```
/
```

这时，系统盘中的目录才会出现在 Guest 中：

```
/
├── etc
├── usr
├── home
├── mnt
│   └── agent-data
├── workspace
└── var
```

完整过程为：

```
/srv/fc/artifacts/agent-rootfs.ext4
    ↓ 项目脚本建立硬链接
Jailer中的/rootfs.ext4
    ↓ Firecracker注册为虚拟块设备
Guest中的/dev/vda
    ↓ Guest内核根据root=/dev/vda挂载
Guest根目录/
```

这一阶段的职责关系是：

- 系统盘构建脚本：提前在系统盘中准备 Linux 文件和 `/mnt/agent-data` 空目录。
- 项目启动脚本：决定使用哪一个系统盘，并生成磁盘配置和内核启动参数。
- Firecracker：把系统盘镜像提供为 Guest 虚拟块设备。
- Guest Linux内核：识别 `/dev/vda`，并将其挂载为根目录 `/`。

系统盘不是由 `agent-init` 挂载的。因为内核必须先挂载系统盘，才能从系统盘中找到并启动：

```
/usr/local/sbin/agent-init
```

#### 数据盘的注册

数据盘原文件位于：

```
/srv/fc/volumes/users/<user-id>.ext4
```

该文件内部已经包含一个独立的 ext4 文件系统，其根目录中包括：

```
lost+found
workspace
pi-state
```

启动 microVM 前，项目脚本将数据盘硬链接到 Jailer 目录：

```
/srv/jailer/firecracker/<instance-id>/root/data.ext4
```

项目脚本生成的 `config.json` 中包含：

```bash
{
  "drive_id": "data",
  "path_on_host": "/data.ext4",
  "is_root_device": false,
  "is_read_only": false
}
```

这些字段分别表示：

- `drive_id: data`：该设备在 Firecracker 配置中的标识。
- `path_on_host`：Firecracker 在 Jailer 中读取的数据盘路径。
- `is_root_device: false`：它不是 Guest 根设备。
- `is_read_only: false`：Guest 可以向数据盘写入内容。

Firecracker 读取 Jailer 中的 `/data.ext4`，并将它作为第二块虚拟块设备提供给 Guest。当前配置下，Guest Linux 内核将它识别为：

```
/dev/vdb
```

完整过程为：

```
/srv/fc/volumes/users/<user-id>.ext4
    ↓ 项目脚本建立硬链接
Jailer中的/data.ext4
    ↓ Firecracker注册为虚拟块设备
Guest中的/dev/vdb
```

此时，Guest 只是识别到了 `/dev/vdb` 这块虚拟硬盘。数据盘内部的 `workspace` 和 `pi-state` 还没有显示在 Guest 的目录树中。

`/dev/vdb` 是一个块设备入口，不是目录，因此不能执行：

```
cd /dev/vdb
```

这一阶段的职责关系是：

- 数据盘创建程序：提前创建 ext4 文件系统及其内部目录。
- 项目启动脚本：决定使用哪一个数据盘，并生成 Firecracker 磁盘配置。
- Firecracker：把数据盘镜像提供为 Guest 虚拟块设备。
- Guest Linux内核：识别该设备，并将其表示为 `/dev/vdb`。

数据盘不是根设备，所以 Guest 内核不会像系统盘一样自动把它挂载为 `/`。它需要由 Guest 初始化脚本主动挂载。

#### 数据盘 `mount` 操作

系统盘 `/dev/vda` 被挂载为根目录后，Guest 可以看到系统盘中提前创建的空目录：

```
/mnt/agent-data
```

此时目录状态为：

```
/
└── mnt
    └── agent-data
```

这个空目录来自 `agent-rootfs.ext4`，由系统盘构建脚本在 microVM 启动前创建。它不是 Firecracker 自动创建的，也不是数据盘中的目录。

Guest Linux 内核挂载系统盘后，会根据启动参数运行：

```
/usr/local/sbin/agent-init
```

> 源码位于 Host 的 `/opt/ai-agent-platform/scripts/guest/agent-init.sh`；安装位置 `/usr/local/sbin/agent-init` 位于 Guest 系统盘内。它是 Bash 文本脚本，不是 ext2 格式程序。在 Host 查看镜像内文件需使用只读 debugfs，不能把 Guest 路径误当成 Host 同名路径。

`agent-init` 是项目编写并预装在系统盘中的 Guest 初始化脚本。

当脚本确认实例配置了数据盘后，会执行：

```shell
mount -t ext4 /dev/vdb /mnt/agent-data
```

- `mount`：请求 Linux 内核挂载文件系统。
- `-t ext4`：告诉内核数据盘使用 ext4 文件系统。
- `/dev/vdb`：要挂载的数据盘块设备。
- `/mnt/agent-data`：系统盘中提前创建的挂载点。

`mount` 命令本身是用户态程序。它会向 Guest Linux 内核发出挂载系统调用，由内核完成真正的操作。

Guest 内核收到请求后：

1. 找到 `/dev/vdb` 虚拟块设备；
2. 按照 ext4 格式解析数据盘；
3. 找到数据盘的文件系统根目录；
4. 将该根目录连接到 `/mnt/agent-data`。

挂载前：

```
系统盘中的/mnt/agent-data
└── 空目录

数据盘/dev/vdb
├── lost+found
├── workspace
└── pi-state
```

挂载后：

```
/                                      属于/dev/vda
├── workspace                          属于/dev/vda
└── mnt                                属于/dev/vda
    └── agent-data                     从这里切换到/dev/vdb
        ├── lost+found                 属于/dev/vdb
        ├── workspace                  属于/dev/vdb
        └── pi-state                   属于/dev/vdb
```

这个过程不会把数据复制到系统盘。

‼️ 更准确地说，`/mnt/agent-data` 只是从一个空目录变成了数据盘文件系统的访问入口。

改变的是 Guest Linux 内核在内存中维护的挂载关系：

``` bash
/mnt/agent-data → 数据盘/dev/vdb的文件系统根目录
```

此后访问：

```
/mnt/agent-data/workspace
```

实际访问的是数据盘中的 `workspace` 目录。

所以这也是为什么看似在只读系统盘里但是仍然可以去进行写操作，实际上  `mount` 后 `/mnt/agent-data/` 实际上就属于 `vdb` 了

完整过程为：

```
系统盘中的空目录/mnt/agent-data
                    ↑
/dev/vdb中的ext4文件系统
    ↓ agent-init发出mount请求
Guest Linux内核完成挂载
    ↓
数据盘根目录通过/mnt/agent-data显示
```

这一阶段的职责关系是：

- 系统盘构建脚本：提前创建 `/mnt/agent-data` 空目录。
- Firecracker：把数据盘提供为 `/dev/vdb`。
- `agent-init`：执行 `mount` 命令，提出挂载请求。
- Guest Linux内核：解析数据盘文件系统，并把它连接到 `/mnt/agent-data`。

数据盘完成整体挂载后，`agent-init` 还会继续通过 bind mount，将其中两个子目录放到 Pi Agent 实际使用的位置：

```
/mnt/agent-data/workspace → /workspace
/mnt/agent-data/pi-state  → /home/pi/.pi
```

#### 数据目录 `bind mount`

数据盘 `/dev/vdb` 挂载完成后，Guest 已经可以通过下面的路径访问整块数据盘：

```
/mnt/agent-data
```

数据盘内部包含两个主要目录：

```
/mnt/agent-data
├── workspace
└── pi-state
    └── agent
```

但是 Pi Agent 不直接使用 `/mnt/agent-data` 作为工作路径。当前项目为 Pi Agent 规定了两个固定位置：

```
/workspace       Pi Agent的工作目录
/home/pi/.pi     Pi Agent的配置和状态目录
```

因此，Guest 初始化脚本需要通过 bind mount，把数据盘中的两个子目录放到 Pi Agent 实际使用的位置。

#### Pi Agent程序 / 工作区 / 状态目录

Pi Agent 运行环境可以分成三个部分。

##### Pi Agent 程序本身

Pi Agent、Node.js 和 Guest 脚本安装在只读系统盘中，主要位于：

```
/usr/local
```

这些属于公共运行环境，由所有实例复用，不应该被普通用户修改。

例如：

```
/usr/local/bin/node
/usr/local/bin/pi
/usr/local/sbin/agent-init
/usr/bin/socat
/usr/local/sbin/pi-rpc-session
```

> `socat`负责监听 Guest 的 TCP 8080 端口，并把每条 TCP 连接桥接到 Pi RPC 进程的 stdin/stdout。`pi-rpc-session`负责准备 Pi 的运行参数，最终以`pi --mode rpc`启动 Pi Agent。socat 以 `-t 30` 运行，连接关闭后给 wrapper 足够时间做 `pi` 退出 + `sync` 刷盘，避免默认 `-t 0.5` 提前杀掉刷盘进程导致 Session 空文件（见 `Pi会话异步落盘竞态问题报告.md`）。

##### Pi Agent 工作目录

Pi Agent 以 `pi` 用户运行，UID 和 GID 为：

```
1001:1001
```

平台 Workspace 任务的当前工作目录由 `pi-rpc-session` 根据首条命令选择：

```
/workspace/workspaces/<workspace-id>
```

没有 workspace 字段的临时调试使用 `/workspace`。下文以 `/workspace` 作为数据盘总入口解释 bind mount。

该目录用于保存：

```
用户上传的文件
项目源代码
Agent读取的文档
Agent创建的文件
任务生成的结果
下载的资源
```

例如 Pi Agent 写入：

```
/workspace/report.md
```

该文件应该在 microVM 停止后继续保留，因此不能写入只读系统盘。

##### Pi Agent 配置和状态目录

`pi` 用户的主目录是：

```
/home/pi
```

Pi Agent 默认使用下面的目录保存自己的配置和状态：

```
/home/pi/.pi
```

其中可能包含：

```
/home/pi/.pi
└── agent
    ├── models.json
    ├── sessions
    └── 其他Pi运行状态
```

主要用途包括：

- `models.json`：保存 Pi 使用的模型名称和 Provider 路由配置；
- `sessions`：启用本地会话保存后产生的会话数据；
- 其他文件：Pi Agent 运行过程中需要持久化的状态。

新会话使用 Pi 原生 Session，首次执行后生成 JSONL；没有平台 Session ID 的临时任务才使用 `--no-session`。

真实模型 API Key 不应该存放在这里。该目录最多保存模型名称、网关地址和占位凭据。

#### `bind mount` 之前

系统盘构建时已经提前创建：

```
/workspace
/home/pi/.pi
/mnt/agent-data
```

数据盘挂载前，这些目录都属于系统盘：

```
系统盘/dev/vda
└── /
    ├── workspace
    ├── home
    │   └── pi
    │       └── .pi
    │           └── agent
    └── mnt
        └── agent-data
```

其中：

`/workspace` 是系统盘预设的工作区挂载目标；

`/home/pi/.pi` 是 Pi 状态目录的预设挂载目标，系统盘中可能已经包含初始化所需的目录结构；

`/mnt/agent-data` 是数据盘的总挂载点。

当初始化脚本执行：

```
mount -t ext4 /dev/vdb /mnt/agent-data
```

数据盘根目录会显示在：

```
/mnt/agent-data
├── lost+found
├── workspace
└── pi-state
    └── agent
```

此时 Guest 中同时存在两组不同目录：

```
系统盘中的/workspace
数据盘中的/mnt/agent-data/workspace
```

以及：

```
系统盘中的/home/pi/.pi
数据盘中的/mnt/agent-data/pi-state
```

在 bind mount 之前，这两组目录彼此独立。

如果 Pi Agent 此时直接写入 `/workspace`，数据会尝试进入系统盘，而系统盘是只读的，所以写入会失败。

#### 执行 `bind mount`

Guest 初始化脚本 `agent-init` 执行：

```
mount --bind /mnt/agent-data/workspace /workspace
```

该命令表示：

```
源目录：/mnt/agent-data/workspace
目标目录：/workspace
```

然后执行：

```
mount --bind /mnt/agent-data/pi-state /home/pi/.pi
```

该命令表示：

```
源目录：/mnt/agent-data/pi-state
目标目录：/home/pi/.pi
```

`mount --bind` 是用户态命令。它向 Guest Linux 内核发出 bind mount 请求，由内核在目录树中建立新的挂载关系。

这里的职责分别是：

- 项目的 `agent-init`：决定源目录和目标目录；
- `mount` 命令：向 Guest 内核发出挂载请求；
- Guest Linux 内核：建立实际的 bind mount；
- Pi Agent：继续使用 `/workspace` 和 `/home/pi/.pi`，不需要了解底层数据盘位置。



#### `bind mount` 之后

完成 bind mount 后：

```
/mnt/agent-data/workspace
/workspace
```

成为同一份数据的两个访问入口。

同时：

```
/mnt/agent-data/pi-state
/home/pi/.pi
```

也成为同一份数据的两个访问入口。

从 Pi Agent 的角度看到：

```
/
├── workspace
│   └── 数据盘中的工作区文件
│
└── home
    └── pi
        └── .pi
            └── agent
                └── 数据盘中的Pi配置和状态
```

从数据盘原始挂载位置看：

```
/mnt/agent-data
├── lost+found
├── workspace
│   └── 与/workspace完全相同
└── pi-state
    └── 与/home/pi/.pi完全相同
```

这里的“相同”不是通过复制或同步实现的，而是因为两个路径访问的是同一个目录对象。

bind mount 前后，Pi Agent 使用的路径保持不变，但路径对应的底层存储发生了切换。系统盘中原有的 `/workspace` 和 `/home/pi/.pi` 被暂时隐藏，同名路径转而指向数据盘中的 `workspace` 和 `pi-state`。因此，Pi Agent 对这些路径的读写最终都会落到可写数据盘，而不会修改只读系统盘。

> 例如 Pi Agent 执行：
>
> ``` bash
> echo hello > /workspace/test.txt
> ```
>
> 同一个文件也可以通过下面的路径访问：
>
> ```
> /mnt/agent-data/workspace/test.txt
> ```
>
> 实际数据保存在数据盘中的：
>
> ```
> workspace/test.txt
> ```
>

#### 原来的系统盘目录隐藏

bind mount 不会删除系统盘中原有的：

```
/workspace
/home/pi/.pi
```

建立 bind mount 后，数据盘目录会暂时覆盖这些路径，系统盘原目录会被隐藏。

关系可以理解为：

```
系统盘原来的/workspace
    ↓ 暂时被遮住
数据盘的/mnt/agent-data/workspace
    ↓ 通过bind mount显示为
/workspace
```

如果解除 bind mount：

```
umount /workspace
```

系统盘中原来的空 `/workspace` 会重新出现。

同理，解除：

```
umount /home/pi/.pi
```

系统盘中原来的 `/home/pi/.pi` 会重新出现。

#### 文件写入宿主机数据盘

当 Pi Agent 向 `/workspace` 写入文件时，并不存在“先写入 Guest，再同步到宿主机”的过程。Guest 发出的文件写入最终会通过虚拟块设备直接修改宿主机上的数据盘镜像。

例如 Pi Agent 执行：

```bash
echo hello > /workspace/test.txt
```

完整写入过程如下：

```
Pi Agent写入/workspace/test.txt
    ↓
Guest Linux内核发现/workspace是bind mount目标
    ↓
将路径解析到/mnt/agent-data/workspace/test.txt
    ↓
发现/mnt/agent-data是/dev/vdb的挂载点
    ↓
Guest ext4文件系统确定需要修改的inode和数据块
    ↓
Guest内核向/dev/vdb发出块写入请求
    ↓
Firecracker接收虚拟磁盘写入请求
    ↓
Firecracker修改Jailer中的/data.ext4
    ↓
Jailer中的/data.ext4与宿主机持久化数据盘是硬链接
    ↓
修改最终落入/srv/fc/volumes/users/<user-id>.ext4
```

这里涉及的各层职责如下：

| 层面                     | 作用                                         |
| ------------------------ | -------------------------------------------- |
| `/workspace`的bind mount | 将Pi工作路径转向数据盘工作区                 |
| `/mnt/agent-data`的mount | 将数据盘文件系统接入Guest目录树              |
| Guest ext4文件系统       | 把文件修改转换为inode和数据块写入            |
| `/dev/vdb`               | 接收Guest发出的虚拟磁盘读写请求              |
| Firecracker              | 将虚拟磁盘读写转换为宿主机文件读写           |
| Jailer硬链接             | 让Jailer路径与持久化路径引用同一个数据盘文件 |

因此，Jailer 中的：

```
/data.ext4
```

与宿主机中的：

```
/srv/fc/volumes/users/<user-id>.ext4
```

不是两份需要同步的数据，而是两个路径指向同一个 inode。Firecracker 修改 Jailer 中的 `/data.ext4` 时，实际上就是在修改宿主机持久化数据盘的同一份底层数据。

> Guest 对 `/workspace` 和 `/home/pi/.pi` 的写入会沿着 bind mount、ext4 文件系统、虚拟块设备和 Firecracker，直接落到宿主机的数据盘镜像中，不需要在实例停止时再复制一次数据。
>
> 但 Linux 可能暂时将最近的写入保存在内存缓存中，因此正常停止实例前仍应执行文件系统同步或正常关机，确保缓存中的数据写入数据盘。强制终止 Firecracker 可能导致最后一小部分尚未落盘的数据丢失，但不会改变持久化数据盘本身的保存机制。

#### 为什么要这样设计

第一，保持系统盘只读。

Pi Agent 程序保存在只读系统盘中，用户文件和运行状态进入可写数据盘。这样可以避免 Agent 修改基础运行环境。

第二，保证用户数据持久化。

microVM 停止后，Jailer 目录和 Firecracker 进程可以被清理，但数据盘仍然保存在：

```
/srv/fc/volumes
```

再次启动 microVM 并挂载同一数据盘后，原来的工作区和 Pi 状态可以继续使用。

第三，保持Pi Agent使用标准路径。

Pi Agent 仍然使用：

```
/workspace
/home/pi/.pi
```

不需要知道数据盘实际挂载在：

```
/mnt/agent-data
```

第四，一块数据盘可以保存两类数据。

```
workspace    保存用户文件和任务产物
pi-state     保存Pi Agent配置和状态
```

两类数据在数据盘中保持分离，但可以一起持久化和重新挂载。

##### 停止与快照恢复时的磁盘关系

正常停止会退出 VMM、清理 jail 和网络，用户数据盘仍保留。下次冷启动重新建立硬链接，并由 Guest 重新执行 mount 和 bind mount。

快照暂停保存 Guest 内存和虚拟设备状态，用户数据盘作为独立镜像保留。恢复时需继续提供配对的系统盘和数据盘；恢复出的 Guest 内核保留此前挂载状态，不是重新运行一遍初始化脚本。快照不能代替磁盘备份，具体流程见第 2 章的快照模块。

## 2.1 受管实例网络与租约管理

受管实例网络模块负责为每台 microVM 分配独立的私有子网、Host 网关地址、Guest IP、TAP 设备和 nftables 规则，并在实例停止或启动失败后释放这些资源。

当前地址池为：

```
172.29.0.0/16
```

NetworkManager 将地址池划分为多个 `/30` 网络槽位。每个槽位包含四个地址：

```
172.29.0.0    网络地址
172.29.0.1    Ubuntu宿主机网关地址
172.29.0.2    microVM Guest地址
172.29.0.3    广播地址
```

因此，一个 `/30` 槽位用于连接一台 microVM 与 Ubuntu 宿主机。`172.29.0.0/16` 最多可以划分出 16384 个 `/30` 槽位，但实际实例数量还会受到宿主机 CPU、内存和文件描述符等资源限制。

### 2.1.1 地址与通信

平台默认从 `172.29.0.0/16` 地址池中，为每个实例分配一个 `/30` 子网。该地址池理论上可划分为 16384 个槽位，实际运行数量还受宿主机资源限制。

#### 子网划分

每个 `/30` 子网包含四个地址：网络地址、两个设备地址和广播地址。

| 用途     | 槽位 0                       | 槽位 1       |
| -------- | ---------------------------- | ------------ |
| 网络地址 | `172.29.0.0`                 | `172.29.0.4` |
| Host IP  | `172.29.0.1`   TAP 虚拟网卡  | `172.29.0.5` |
| Guest IP | `172.29.0.2`   eth0 虚拟网卡 | `172.29.0.6` |
| 广播地址 | `172.29.0.3`                 | `172.29.0.7` |

网络地址和广播地址不分给普通设备。代码固定将子网起始地址加 `1` 分给 Host，加 `2` 分给 Guest。

相邻槽位的起始地址依次为 `.0`、`.4`、`.8`。下一台实例会选择下一个可用槽位，遇到占用时会继续跳过。

#### 地址写法

```
172.29.0.2/30
```

表示：**设备自身的 IP 是 `172.29.0.2`，它属于 `172.29.0.0/30` 子网。**

它不是说 Guest 同时占用四个地址。

| 写法            | 当前配置中的含义           |
| --------------- | -------------------------- |
| `172.29.0.0/30` | 整个子网                   |
| `172.29.0.1/30` | Host 的接口地址及子网前缀  |
| `172.29.0.2/30` | Guest 的接口地址及子网前缀 |

Host IP 配置在 Ubuntu 宿主机的 TAP 上，Guest IP 配置在 microVM 的 `eth0` 上。一个宿主机可以通过多个 TAP，分别使用各实例对应的 Host IP。

#### 配置位置

TAP、MAC、Guest IP 和 Host IP，都能在实例的 `config.json` 中找到：

| 信息      | 配置位置                           | 示例                |
| --------- | ---------------------------------- | ------------------- |
| TAP       | `network-interfaces.host_dev_name` | `fc00000000`        |
| Guest MAC | `network-interfaces.guest_mac`     | `06:00:ac:1d:00:00` |
| Guest IP  | `boot_args` 中的 `agent_ip`        | `172.29.0.2/30`     |
| Host IP   | `boot_args` 中的 `agent_gateway`   | `172.29.0.1`        |

Firecracker 读取 TAP 和 MAC，连接虚拟网卡；Guest 内的 `agent-init` 读取 IP 和网关参数，配置 Guest 网络。

Host IP 在生成配置前已经设置到宿主机 TAP 上。写入 `agent_gateway`，是为了告诉 Guest 网关的位置。

#### 模型访问

Guest IP 和 Host IP 用于 microVM 与宿主机之间的通信：

```
Guest：172.29.0.2
    │ 请求 http://172.29.0.1:18082/v1
    ↓
宿主机 Tool Gateway：172.29.0.1:18082
    │ 另行发起 HTTPS 请求
    ↓
外网模型服务：https://api.deepseek.com
```

Pi Agent 使用 Guest IP 请求宿主机 Gateway，不直接连接外网模型。

Gateway 再使用 Ubuntu 宿主机的出网接口访问模型服务，具体来源地址由系统路由决定；经过 NAT 后，外部服务通常看到的是出口公网 IP。

### 2.1.2 NetworkAddressPool：计算实例网络配置

代码位置：`services/instance-manager/network_manager.py`。

`NetworkAddressPool` 负责根据地址池和槽位编号，计算一个实例所需的网络配置，包括子网、Host IP、Guest IP、MAC 地址、TAP 名称和 nftables 表名。

它相当于一个地址计算器：给定相同的地址池和槽位编号，就得到相同的网络参数。

这个类不查询已使用槽位，不读写租约文件，也不执行 Linux 网络命令。它生成的字典需要交给后续组件，才能完成租约登记和真实网络创建。

####  `__init__()`：校验地址池并计算槽位容量

初始化时接收两个参数：

```
NetworkAddressPool("172.29.0.0/16", 30)
```

其中，`172.29.0.0/16` 是总地址池，`30` 表示每个实例默认使用一个 `/30` 子网。

**1. 将地址池字符串转换成网络对象**

```python
self.network = ipaddress.ip_network(pool)
self.prefix_length = prefix_length
```

`ipaddress` 是 Python 自带的网络地址处理模块。`ip_network()` 将字符串转换成网络对象，方便读取和计算：

```python
self.network.version          → 4
self.network.prefixlen        → 16
self.network.network_address  → 172.29.0.0
```

这里仅解析地址，不会修改 Ubuntu 的网络配置。

**2. 检查地址池和槽位前缀是否符合要求**

```python
if self.network.version != 4:
    raise NetworkFailure("network pool must be IPv4")

if prefix_length <= self.network.prefixlen or prefix_length > 30:
    raise NetworkFailure("network pool must contain /30-or-larger slots")
```

当前实现只接受 IPv4。

槽位前缀必须大于总地址池前缀，保证能够将地址池继续划分；同时不能大于 `30`，保证每个槽位至少有四个地址，供当前的 Host、Guest 地址分配方式使用。

默认使用 `/30`，代码也允许符合检查条件、地址数量更多的子网。

**3. 计算总槽位数**

```python
self.slot_count = 1 << (prefix_length - self.network.prefixlen)
```

`1 << n` 在这里相当于计算 `2ⁿ`。

默认配置下：

```
槽位数 = 2^(30 - 16)
       = 16384
```

这表示地址池理论上能划分出 16384 个槽位，并不代表已经创建了这些网络，也不代表宿主机能同时运行这么多实例。

**4. 计算每个槽位的地址数量**

```python
self.block_size = 1 << (32 - prefix_length)
```

IPv4 地址总长为 32 位，因此 `/30` 子网包含：

```
每个槽位地址数 = 2^(32 - 30)
               = 4
```

`block_size` 也是相邻槽位起始地址之间的间隔：

```
slot 0 → 172.29.0.0/30
slot 1 → 172.29.0.4/30
slot 2 → 172.29.0.8/30
```

初始化完成后，对象保存了地址池、槽位前缀、总槽位数和每个槽位的地址数量。

#### `build_lease()`：根据槽位生成网络配置

这个方法接收实例 ID 和槽位编号，返回一个网络配置字典：

```python
lease = address_pool.build_lease("cli-demo", 0)
```

方法名虽然叫 `build_lease()`，但此时只是生成候选配置；租约的登记、状态和时间戳由存储层处理。

**1. 计算槽位起始地址**

```python
address = int(self.network.network_address) + slot * self.block_size
```

计算公式为：

```
槽位起始地址 = 地址池起始地址 + 槽位编号 × 每槽位地址数
```

`int()` 将网络地址转换成整数，以便进行加法。

例如槽位 `1`：

```
172.29.0.0 + 1 × 4 → 172.29.0.4
```

**2. 生成该槽位的子网对象**

```python
subnet = ipaddress.ip_network((address, self.prefix_length))
```

把起始地址和前缀长度组合起来。槽位 `1` 得到：

```
172.29.0.4/30
```

**3. 计算 Host 和 Guest 地址**

```python
host_ip = str(subnet.network_address + 1)
guest_ip = str(subnet.network_address + 2)
```

`subnet.network_address` 是该子网的网络地址。代码将其后的第一个地址分给 Ubuntu 宿主机，第二个地址分给 microVM。

以槽位 `0` 为例：

| 地址         | 用途                       |
| ------------ | -------------------------- |
| `172.29.0.0` | 网络地址，代表整个子网     |
| `172.29.0.1` | Host：配置在宿主机 TAP 上  |
| `172.29.0.2` | Guest：供 microVM 网卡使用 |
| `172.29.0.3` | 广播地址                   |

`str()` 将地址对象转换成字符串，方便保存和传递。

**4. 根据槽位生成资源名称和 MAC 地址**

```python
"tap": f"fc{slot:08x}",
"nft_table": f"aap_{slot:08x}",
```

`:08x` 表示将槽位编号转换成十六进制，至少显示八位，不足时在前面补零。

例如：

```
slot 0 → fc00000000 / aap_00000000
slot 1 → fc00000001 / aap_00000001
```

MAC 地址使用固定前缀，并将槽位编号编码到最后两个字节：

```
"guest_mac": f"06:00:ac:1d:{(slot >> 8) & 0xff:02x}:{slot & 0xff:02x}"
```

其中，`>> 8` 配合 `& 0xff` 提取较高的一个字节，`slot & 0xff` 提取最低的一个字节，`:02x` 将每个字节显示为两位十六进制。

例如：

```
slot 0   → 06:00:ac:1d:00:00
slot 1   → 06:00:ac:1d:00:01
slot 256 → 06:00:ac:1d:01:00
```

**5. 返回完整配置字典**

槽位 `0` 的返回结果如下：

```python
{
    "instance_id": "cli-demo",
    "slot": 0,
    "subnet": "172.29.0.0/30",
    "host_ip": "172.29.0.1",
    "host_cidr": "172.29.0.1/30",
    "guest_ip": "172.29.0.2",
    "guest_cidr": "172.29.0.2/30",
    "guest_mac": "06:00:ac:1d:00:00",
    "tap": "fc00000000",
    "nft_table": "aap_00000000",
    "nft_family": "inet",
}
```

其中，`host_cidr` 和 `guest_cidr` 是带前缀长度的地址，供后续配置网卡使用；`nft_family` 指定防火墙表使用 `inet` 协议族。

这份结果尚未包含 `status`、`created_at` 和 `updated_at`。后续由 `SQLiteLeaseStore.reserve()` 登记时添加这些字段。

`NetworkManager.allocate()` 会使用这份候选配置检查资源占用，并尝试登记租约。只有后面的 `setup()` 才会调用 Linux 网络工具，真正创建相应资源。

### 2.1.3 LeaseStore：定义租约存储接口

代码位置：`services/instance-manager/network_manager.py`。

`LeaseStore` 规定网络管理流程需要哪些存储操作，本身不保存数据。当前正式实现为 `SQLiteLeaseStore`；历史 `FileLeaseStore` 仅保留旧 JSON 实例清理兼容。

#### 接口的实现方式

```python
class LeaseStore:
    def list(self) -> list[dict]:
        raise NotImplementedError

    def get(self, instance_id: str) -> dict | None:
        raise NotImplementedError

    def reserve(self, lease: dict) -> dict:
        raise NotImplementedError

    def set_status(self, instance_id: str, status: str) -> dict:
        raise NotImplementedError

    def release(self, instance_id: str) -> None:
        raise NotImplementedError
```

父类相当于一份操作约定，子类提供具体实现。当前使用普通 Python 基类；遗漏实现的方法会在调用时抛出 `NotImplementedError`。

#### `list()`：读取全部租约

不需要实例 ID，返回按槽位排序的租约字典列表；没有记录时返回 `[]`。

```python
[
    {"instance_id": "agent-one", "slot": 0, ...},
    {"instance_id": "agent-two", "slot": 1, ...},
]
```

`NetworkManager.allocate()` 用它收集已登记槽位。这是查询数据库，不是扫描 Linux 设备。

#### `get()`：查询指定实例的租约

接收 `instance_id`，找到时返回字典，未找到返回 `None`。

```python
lease = store.get("cli-demo")
```

管理器用它避免为同一实例重复分配，并在释放时取得原网络配置。

#### `reserve()`：登记并预留租约

接收地址计算器返回的候选配置，添加 `reserved`、创建时间和更新时间后保存，返回保存后的租约。

数据库中的事务和唯一约束处理最终冲突。冲突抛出 `LeaseConflict`，上层可尝试下一个槽位。该方法只登记，不创建 TAP。

#### `set_status()`：更新租约状态

接收实例 ID 和状态，更新 `status`、`updated_at`，返回更新后的记录。

| 状态 | 含义 |
|---|---|
| `reserved` | 网络槽位已预留 |
| `active` | 上层确认实例就绪 |
| `releasing` | 正在清理 Linux 网络 |
| `error` | 创建回滚或释放存在残留 |

方法验证状态名称和记录是否存在，不检测 Guest，也不强制完整状态迁移顺序。

#### `release()`：删除租约记录

接收实例 ID，删除记录，不返回数据。记录不存在时可重复执行。

| 方法 | 职责 |
|---|---|
| `LeaseStore.release()` 的具体实现 | 删除存储记录 |
| `NetworkManager.release()` | 先清理 Linux 资源，确认完成后删除记录 |

因此上层正常释放使用 `NetworkManager.release()`。

#### 与管理器、具体存储实现的关系

```python
store = SQLiteLeaseStore(Path("/var/lib/fc/control-plane.db"))
manager = NetworkManager(store, allow_host_connections=True)
```

管理器调用 `self.store.get(instance_id)` 时，实际运行 `SQLiteLeaseStore.get()`。地址计算器和 Linux 网络驱动只使用租约字典，不需要知道数据保存到哪种数据库。

### 2.1.4 SQLiteLeaseStore：读取和保存网络租约

代码位置：`services/instance-manager/network_manager.py`。

`SQLiteLeaseStore` 继承 `LeaseStore`，将正式租约保存到统一控制面数据库：

```text
/var/lib/fc/control-plane.db
    └── network_leases
```

它只管理记录，不计算槽位、不创建 TAP，也不维护长期网络后台线程。

#### `__init__()`：确定数据库路径

接收 `database_path: Path`，解析绝对路径、创建父目录并调用 `initialize()`。默认路径由 `InstanceRuntime` 传入，测试可使用临时数据库。

```python
self.database_path = database_path.resolve()
self.initialize()
```

#### `connect()`：管理一次数据库操作

```python
connection = sqlite3.connect(self.database_path, timeout=10)
connection.row_factory = sqlite3.Row
```

连接成功后，调用者在上下文中执行 SQL。正常结束提交，异常时回滚，最后关闭连接。`timeout=10` 允许短暂等待写锁；`sqlite3.Row` 支持按列名取值。

SQLite 负责数据库并发协调。WAL 允许读操作和写事务较好共存，但同一时刻仍只有一个写事务。

#### `initialize()`：创建表与约束

初始化幂等创建 `network_leases`，设置 WAL，并将数据库文件权限设为 `0600`。

| 字段 | 作用与约束 |
|---|---|
| `instance_id` | 主键，同实例最多一条租约 |
| `slot` | 非负且唯一的槽位编号 |
| `subnet` | 唯一的子网 |
| `host_ip / host_cidr` | Host TAP 地址 |
| `guest_ip / guest_cidr` | Guest eth0 地址 |
| `guest_mac` | 唯一 MAC |
| `tap` | 唯一 TAP 名称 |
| `nft_table / nft_family` | 唯一表名及 nft 协议族 |
| `status` | reserved、active、releasing、error 四选一 |
| `created_at / updated_at` | Unix 秒级时间戳 |

另外创建 `status,slot` 索引。数据库约束保护登记一致性，不负责判断 Linux 资源是否已经存在。

#### `list()`：读取全部租约

```sql
SELECT * FROM network_leases ORDER BY slot
```

查询结果通过 `_row_to_dict()` 转成普通字典列表，交给管理器使用。

#### `get()`：查询一个实例

```sql
SELECT * FROM network_leases WHERE instance_id=?
```

实例 ID 通过参数绑定传入，不直接拼进 SQL 字符串。没有行时返回 `None`。

#### `reserve()`：通过事务预留槽位

接收候选租约，构造字段值并在写事务中插入：

```text
BEGIN IMMEDIATE
    ↓
INSERT network_leases，status=reserved
    ↓
提交
    ↓
读取并返回保存的租约
```

`BEGIN IMMEDIATE` 提前取得写事务，唯一约束负责拒绝重复实例、槽位、子网或设备名称。代码将 `sqlite3.IntegrityError` 转换为 `LeaseConflict`，管理器继续尝试其他槽位。

先查询再插入之间仍可能有并发变化，所以前面的“空闲检查”不能替代这里的事务与约束。

#### `set_status()`：更新状态与时间

```sql
UPDATE network_leases SET status=?,updated_at=? WHERE instance_id=?
```

更新后检查影响行数；不是一行时报告租约不存在。成功后再查询并返回记录。

#### `release()`：删除完成清理的租约

```sql
DELETE FROM network_leases WHERE instance_id=?
```

此处不执行 `ip`、`nft`，也不删除磁盘镜像。管理器确认 Linux 网络清理完成后才调用。

#### 历史 FileLeaseStore 的保留用途

旧 `FileLeaseStore` 仍位于同一文件中，通过 JSON、文件锁及临时文件替换保存旧租约。只有生命周期元数据包含旧 `networkLeasePath` 时，兼容清理分支才使用它。

新实例和正常查询使用 SQLite。保留该兼容类不代表当前需要再部署一套 JSON 租约账本。

### 2.1.5 LinuxNetworkDriver：创建和清理真实 Linux 网络

代码位置：`services/instance-manager/network_manager.py`。

`LinuxNetworkDriver` 接收租约中的网络配置，通过执行 `ip`、`nft` 命令操作 Ubuntu 宿主机。

它负责三类工作：

- 查询候选网络资源是否被占用。
- 创建 TAP、配置宿主 IP、安装防火墙规则。
- 删除网络资源，并检查是否存在残留。

它不选择槽位、不读写数据库，也不更新租约状态。这些工作分别由地址计算、存储和管理组件负责。

#### 2.1.5.1 `__init__()`：设置命令执行方式和访问选项

```python
def __init__(self, runner=None, *, allow_host_connections: bool = False):
    self.runner = runner or run_command
    self.allow_host_connections = allow_host_connections
```

初始化保存两个设置。

**命令执行工具 `runner`**

默认使用本文件中的 `run_command()` 执行真实 Linux 命令。测试时可以传入模拟执行器，在内存中模拟资源变化，不创建真实网络。

```python
self.runner = runner or run_command
```

这里保存的是函数，尚未执行命令。

**宿主连接响应选项 `allow_host_connections`**

默认关闭。当前 `InstanceRuntime` 显式开启它，允许 Guest 返回宿主机主动建立的 TCP 连接响应，供 Host Pi Gateway 使用。

初始化本身不会创建网络资源。

#### 2.1.5.2 `_validate_lease()`：检查资源名称和协议族

在执行网络操作前，从租约中取出：

```python
tap = str(lease["tap"])
table = str(lease["nft_table"])
family = str(lease.get("nft_family", "inet"))
```

然后检查：

| 配置            | 检查条件                               |
| --------------- | -------------------------------------- |
| TAP 名称        | 不超过 15 个字符，且符合允许的字符规则 |
| nftables 表名   | 符合允许的字符规则                     |
| nftables 协议族 | 必须为 `inet`                          |

允许的名称字符在文件开头定义：

```
VALID_RESOURCE_NAME = re.compile(r"^[A-Za-z0-9_.-]+$")
```

即字母、数字、下划线、点和短横线。

不符合要求时，抛出 `NetworkFailure`，阻止继续操作。这个方法只检查上述资源字段，不是对租约全部内容进行完整校验。

#### 2.1.5.3 `_resource_exists()`：通过查询命令判断资源是否存在

```python
result = self.runner(arguments, check=False)
return result.returncode == 0
```

例如查询 TAP：

```
ip link show dev fc00000000
```

或者查询防火墙表：

```
nft list table inet aap_00000000
```

`check=False` 表示命令返回非零退出码时，不自动抛出命令执行异常。

该方法将退出码 `0` 视为查询成功，返回 `True`；其他退出码返回 `False`。

因此，它是一个基于命令执行结果的存在性判断，没有进一步区分“资源不存在”和“权限不足等查询失败”。

#### 2.1.5.4 `resources_are_free()`：检查候选网络资源是否空闲

这个方法用于回答：**候选租约对应的 Linux 资源，现在能不能使用？**

先调用 `_validate_lease()`，然后依次检查三项。

**1. 是否已有相同子网的路由**

```
ip -4 route show exact 172.29.0.0/30
```

如果输出非空，说明查询到了对应路由，返回 `False`。

这里检查的是相同子网的精确路由，不是扫描所有可能重叠的网络。

**2. TAP 名称是否已存在**

```
ip link show dev fc00000000
```

存在则返回 `False`，避免使用已占用的设备名称。

**3. 防火墙表名是否已存在**

```
nft list table inet aap_00000000
```

存在则返回 `False`。

三项检查均未发现占用，才返回 `True`。

`NetworkManager.allocate()` 使用它筛选候选槽位；`create()` 在真正创建前还会再次检查，因为两次操作之间的系统状态可能变化。

#### 2.1.5.5 `_build_firewall_rules()`：生成实例访问控制规则

这个方法只生成规则文本，不执行 `nft` 命令。

**1. 整理并检查允许访问的端口**

```
ports = tuple(sorted({int(port) for port in allowed_host_ports}))
```

依次完成整数转换、去重和排序，再检查端口列表非空，且每个端口位于 `1～65535`。

端口由调用者传入。例如：

| 使用场景     | 传入端口                  |
| ------------ | ------------------------- |
| 当前受管实例 | `18082`（模型网关） |

因此，这个类没有把所有场景的端口写死。

**2. 为实例生成独立的防火墙表**

例如槽位 `0`：

```
table inet aap_00000000
```

表内包含 `input` 和 `forward` 两条基础链，挂接优先级均为 `-10`，默认策略为 `accept`。

`inet` 表可以处理 IPv4 和 IPv6，但当前生成的地址匹配规则使用 IPv4。

**3. 控制 Guest 发往宿主机的流量**

`input` 链处理目标为宿主机本身的流量。

核心放行规则要求同时匹配：

```
入口设备：该实例的 TAP
来源 IP：该实例的 Guest IP
目标 IP：该实例的 Host IP
协议：TCP
目标端口：调用者允许的端口
```

例如：

```
iifname "fc00000000"
ip saddr 172.29.0.2
ip daddr 172.29.0.1
tcp dport { 18082 }
counter accept
```

随后，对来自该 TAP、源地址匹配该 Guest IP、但未被前面规则放行的流量执行 `drop`。

`counter` 用来统计匹配的包数和字节数。

这些是本模块添加的规则；流量最终是否可达，还会受到宿主机其他防火墙规则和服务监听状态的影响。

**4. 放行宿主机主动连接的响应**

开启 `allow_host_connections` 时，在丢弃规则之前加入：

```
iifname "fc00000000"
ip saddr 172.29.0.2
ip daddr 172.29.0.1
ct state established,related
counter accept
```

它用于接收 Guest 对宿主机主动连接的响应，不是放开 Guest 任意访问宿主机端口。

**5. 阻止通过该 TAP 转发流量**

`forward` 链处理经过宿主机、需要转发到其他地方的流量：

```
iifname "fc00000000" counter drop
oifname "fc00000000" counter drop
```

一条阻止从该 TAP 进入的转发流量，另一条阻止转发到该 TAP 的流量。

宿主机直接连接 Guest 的 Pi RPC 属于宿主机本地产生的流量，不经过 `forward` 链。

#### 2.1.5.6 `_install_firewall()`：将规则提交给 nftables

安装过程为：

```
创建临时 .nft 文件
    ↓
写入完整规则文本
    ↓
执行 nft -f
    ↓
删除临时文件
```

核心命令：

```
self.runner(["nft", "-f", str(rules_path)])
```

`nft -f` 从文件读取规则并提交给内核。

成功安装后，规则由 Linux 内核维护，不依赖临时文件继续存在。因此，删除临时文件不会撤销规则。

如果安装命令失败，异常会交给 `create()`，由它组织回滚。

#### 2.1.5.7 `create()`：创建一套实例网络资源

这是实际创建网络的主要入口。它接收：

- `lease`：已预留的网络配置。
- `firecracker_uid`：允许使用 TAP 的 Linux 用户编号。
- `allowed_host_ports`：Guest 可以访问的宿主机 TCP 端口。

执行顺序如下。

**1. 检查配置、生成规则、再次检查占用**

```python
self._validate_lease(lease)
rules = self._build_firewall_rules(lease, allowed_host_ports)

if not self.resources_are_free(lease):
    raise NetworkFailure(...)
```

发现资源已被占用就报错，不继续创建。

**2. 创建 TAP**

```
ip tuntap add dev fc00000000 mode tap user <firecracker_uid>
```

TAP 是宿主机上的二层虚拟网络设备。`user` 参数允许指定用户使用该 TAP，使低权限 Firecracker 进程能够接入它。

**3. 配置宿主 IP**

```
ip address add 172.29.0.1/30 dev fc00000000
```

地址配置在 Ubuntu 的 TAP 上。Linux 同时会建立对应的直连路由。

Guest IP 此时没有被配置；它由 Guest 内部的初始化流程设置。

**4. 启用 TAP，再安装防火墙规则**

```
ip link set dev fc00000000 up
```

随后调用 `_install_firewall()`，安装前面生成的规则。

**5. 创建失败时尝试撤销**

函数记录了两个标记：

```
tap_created = False
firewall_attempted = False
```

根据执行进度判断本次已创建或尝试安装了哪些资源。

中途失败后：

1. 如果尝试过安装防火墙，调用 `_delete_firewall()`。
2. 如果创建了 TAP，调用 `_delete_tap()`。
3. 调用 `_find_leftovers()` 检查残留。

如果检测到残留，抛出 `NetworkRollbackFailure`；否则继续抛出原始错误。

这里负责网络回滚。租约是否删除、是否标记为 `error`，由上层 `NetworkManager.setup()` 处理。

#### 2.1.5.8 `_delete_firewall()` / `_delete_tap()`：删除指定资源

**删除防火墙表**

先查询表是否存在，再执行：

```
nft delete table inet aap_00000000
```

删除整个实例表，会一并删除表内的链和规则。

**删除 TAP**

先查询设备是否存在，再执行：

```
ip link delete fc00000000
```

删除 TAP 时，设备上的 IP 和关联直连路由也会随之移除，不需要另外删除 IP。

两个删除命令均使用 `check=False`。因此，删除后还要检查残留，不能仅凭命令已执行就认定清理成功。

#### 2.1.5.9 `_find_leftovers()`：查询清理后仍存在的资源

这个方法分别查询防火墙表和 TAP，将仍能查询到的资源名称加入列表。

完全清理时返回：

```
[]
```

存在残留时可能返回：

```python
[
    "nft:inet/aap_00000000",
    "tap:fc00000000",
]
```

它只报告查询结果，不修改租约，也不继续执行删除操作。

#### 2.1.5.10 `remove()`：组织网络清理并返回结果

```python
self._validate_lease(lease)
self._delete_firewall(lease)
self._delete_tap(lease)
return self._find_leftovers(lease)
```

正常执行顺序为：

```
检查资源名称
    ↓
删除防火墙表
    ↓
删除 TAP
    ↓
查询残留
    ↓
返回残留列表
```

`NetworkManager.release()` 根据这个列表决定下一步：

| 清理结果   | 上层处理                      |
| ---------- | ----------------------------- |
| 没有残留   | 删除租约记录                  |
| 检测到残留 | 保留租约，标记 `error` 并报错 |

因此，`remove()` 负责清理和报告，管理器负责租约状态及记录。

#### 2.1.5.11 `run_command()`：执行底层 Linux 命令

`run_command()` 是同一文件中的独立函数，不属于 `LinuxNetworkDriver` 类。它是默认的命令执行器：

```python
return subprocess.run(
    arguments,
    check=check,
    text=True,
    stdout=subprocess.PIPE,
    stderr=subprocess.PIPE,
)
```

它直接接收命令参数列表，不通过 shell 解析：

```python
["ip", "link", "delete", "fc00000000"]
```

同时捕获标准输出、标准错误和退出码：

- `check=True`：非零退出码会抛出异常。
- `check=False`：返回执行结果，由调用者判断。

`LinuxNetworkDriver` 通过 `self.runner(...)` 使用它，也因此能够在本地测试中替换为模拟执行器。

### 2.1.6 NetworkManager：协调网络分配、创建、激活和释放

代码位置：`services/instance-manager/network_manager.py`。

管理器组合三个组件：

| 组件 | 管理器使用的能力 |
|---|---|
| `SQLiteLeaseStore`（通过 LeaseStore 接口） | 查询、预留、更新和删除租约 |
| `NetworkAddressPool` | 按 slot 计算网络参数 |
| `LinuxNetworkDriver` | 查询、创建、清理 Linux 网络 |

`allocate()`、`setup()`、`activate()` 是分开的操作。实例启动流程按顺序调用；创建网络成功不代表 Guest 已就绪。

#### 2.1.6.1 `__init__()`：组合存储、地址计算和网络操作工具

输入为存储对象、地址池、槽位前缀、命令执行器和 Host 响应选项：

```python
self.store = store
self.address_pool = NetworkAddressPool(pool, prefix_length)
self.network = LinuxNetworkDriver(runner, allow_host_connections=allow_host_connections)
```

默认池为 `172.29.0.0/16`，前缀为 `/30`。正式实例使用 SQLite 并开启 `allow_host_connections=True`。构造对象只准备工具，不创建网络。

#### 2.1.6.2 `allocate()`：选择空闲槽位并预留租约

输入 `instance_id`，输出完整的 `reserved` 租约。

```text
拒绝同实例未释放租约
    ↓
读取已登记的 slot
    ↓
按序计算候选配置
    ↓
检查精确路由、TAP、nft表是否空闲
    ↓
SQLite reserve() 执行最终登记
    ↓
成功返回；唯一约束冲突则继续下一候选
```

数据库中任何状态的记录都会占用槽位。Linux 检查再补充发现“账本没有、系统仍有”的资源残留。当前检查精确子网路由，不是完整的网段重叠检测。

默认槽位范围为 0～16383，耗尽后抛出 `NetworkFailure`。返回仅表示预留完成。

#### 2.1.6.3 `setup()`：创建网络并处理创建失败

输入租约、Firecracker UID 和允许访问的 Host TCP 端口，例如：

```python
manager.setup(lease, firecracker_uid, (18082,))
```

实际操作委托 `LinuxNetworkDriver.create()`。

| 结果 | 租约处理 |
|---|---|
| 创建成功 | 仍为 reserved，等待 Guest 就绪 |
| 创建失败且回滚有残留 | 标记 error，保留记录并抛出异常 |
| 创建失败且已完成回滚 | 删除预留记录并抛出异常 |

`setup()` 不启动 Firecracker，也不检测 Pi RPC。

#### 2.1.6.4 `activate()`：标记网络生效

输入实例 ID，调用：

```python
self.store.set_status(instance_id, "active")
```

冷启动由 Host 读到 Guest 的就绪标志后调用。快照恢复由恢复流程加载并恢复 VMM 后调用。该方法只更新记录，不独立进行健康检查。

#### 2.1.6.5 `release()`：先清理网络，再删除租约记录

输入实例 ID，可选传入运行元数据中的兜底 `lease`。

```text
先查数据库租约，缺失则使用兜底配置
    ↓
两者都没有 → 幂等结束
    ↓
有数据库记录 → 标记 releasing
    ↓
LinuxNetworkDriver.remove() 删除表与 TAP
    ↓
有残留 → 已有租约标记 error 并保留；仅用兜底配置时直接报错
无残留 → 删除仍存在的租约记录
```

删除 TAP 会同时移除其地址与直连路由。成功后没有永久保留的 `released` 行，而是移除记录。

兜底配置用于资源尚需清理但租约已被另一清理步骤删除的情况，避免停止流程因“租约不存在”重复失败。管理器不停止 VMM，上层应先停止使用网络的进程。

#### 2.1.6.6 租约状态：记录关键操作结果

正常过程为：

```text
allocate → reserved
setup → reserved
Guest就绪 → activate → active
release → releasing → 清理完成 → 删除记录
                         └→ 残留 → error
```

租约状态与业务实例状态是不同字段。修改数据库中的租约状态不会自动创建或删除 TAP；真实资源仍由 Linux 驱动操作。

#### 2.1.6.7 `reserve_snapshot_lease()`：恢复原网络槽位

输入 `instance_id` 和快照 manifest 中保存的租约，重新计算该 slot 的标准配置，并核对子网、Host/Guest IP、MAC、TAP 和 nftables 表名。

确认 Linux 资源空闲后，再通过 SQLite 预留。快照内已保存 Guest 网卡状态，因此恢复不能任意换成另一个 IP。原槽位已被其他实例占用时，当前实现拒绝恢复；它没有为暂停实例永久保留网络槽位。

#### 与生命周期清理的关系

`lifecycle.py` 的 `cleanup_ephemeral()` 读取运行元数据的 `networkDatabasePath`，创建同一 SQLiteLeaseStore，再调用 `NetworkManager.release()`。

旧元数据只有 `networkLeasePath` 时才走 JSON 兼容分支。这样独立空闲回收进程也能使用同一账本完成清理。

## 2.2 Pi RPC 受管通信

当前正式受管实例已使用 Pi RPC。任务经 Control Plane、Agent Runtime 适配器和 Host Pi Gateway，进入 Guest 的 socat，再交给 Pi。旧 Agent Bridge 和 MCP Gateway 已退出当前链路。

槽位 0 的两条连接示例为：

| 端点 | 发起方向 | 作用 |
|---|---|---|
| `172.29.0.2:8080` | Host → Guest | Pi 命令与 JSONL 事件 |
| `172.29.0.1:18082` | Guest → Host | Pi 向模型网关发 HTTP 请求 |

两条 TCP 连接本身都能双向传输，端口表示监听服务所在位置。它们承担不同业务，不能混为一条连接。

### 2.2.1 模块组成

| 模块 | 文件或安装位置 | 实际职责 |
|---|---|---|
| Control Plane | `services/control-plane/server.py` | 任务调度、归属校验和结果保存 |
| Agent Runtime Adapter | `services/agent-runtime/agent_runtime.py` | 提供 execute/get_messages 统一接口 |
| Pi Gateway | `services/pi-gateway/gateway.py` | TCP 连接、JSONL 命令与 Pi 事件适配 |
| Guest init | `scripts/guest/agent-init.sh` | 启动 socat 监听循环 |
| socat | Guest `/usr/bin/socat` | TCP 与进程 stdin/stdout 桥接 |
| Pi 会话入口 | Guest `/usr/local/sbin/pi-rpc-session` | 工作区与 Session 选择、Pi 参数准备 |
| Pi CLI | Guest `/usr/local/bin/pi` | 执行 Agent 循环、调用模型与工具 |

```text
Control Plane
    ↓ AgentRuntimeAdapter.execute()
PiRuntimeAdapter → PiGateway
    ↓ TCP / JSONL
Guest socat
    ↓ stdin / stdout
pi-rpc-session → pi --mode rpc
```

### 2.2.2 Pi RPC 启动过程

`InstanceRuntime.prepare_jail()` 将以下参数写入内核命令行：

```text
agent_managed_runtime=1
agent_ip=<Guest IP>/30
agent_gateway=<Host IP>
agent_rpc_port=8080
agent_rpc_provider=deepseek-gateway
agent_rpc_model=deepseek-flash
```

`agent-init` 读取参数，以非 root 的 pi 用户运行：

```text
socat -t 30 TCP-LISTEN:8080,bind=<Guest IP>,reuseaddr EXEC:/usr/local/sbin/pi-rpc-session
```

当前没有使用 socat 的 `fork` 选项，一次只处理一条 TCP 连接。连接结束后，外层循环重新启动监听器。`-t 30` 给连接关闭后的 `pi` 退出 + `sync` 刷盘留足时间（默认 `-t 0.5` 会提前杀掉刷盘进程，见 `Pi会话异步落盘竞态问题报告.md`）。

监听就绪时输出 `PI_RPC_READY`。客户端连接建立后，socat 先启动会话脚本；脚本等到首条 JSONL，确定工作区与 Session 后才启动 Pi CLI。

### 2.2.3 TCP 与 stdin/stdout 桥接

Pi RPC 通过标准输入接收命令，通过标准输出返回事件。stdin、stdout、stderr 是进程创建时继承的文件描述符，不是需要安装的组件。

socat 建立以下关系：

```text
Host发来的TCP字节 → 会话脚本stdin → Pi stdin
Host收到的TCP字节 ← socat ← Pi stdout
```

Pi 的 stderr 进入 Guest 串口日志，不应混进 RPC JSONL。socat 只传递字节，不负责校验用户、选择任务或转换平台事件。

当前 Pi 基础参数为：

```text
--mode rpc
--offline
--no-approve
--no-extensions
--no-skills
--no-prompt-templates
--no-context-files
--tools read,write
```

模型通过 `--provider deepseek-gateway --model deepseek-flash` 选择。`--offline` 及环境变量用于约束 Pi 的后台行为，不阻止显式配置的 Host 模型网关请求。Session 参数按首条记录动态追加，并非所有连接都使用 `--no-session`。

### 2.2.4 JSONL 协议

JSONL 要求一行一个完整 JSON 对象，以换行符分隔。Host Pi Gateway 发送的第一条任务记录例如：

```json
{"id":"gateway-xxx","type":"prompt","message":"读取当前目录的说明文件","workspace":"workspace-0123456789abcdef","session":"conversation-0123456789abcdef"}
```

| 字段 | 含义 |
|---|---|
| `id` | 将命令与 response 对应起来 |
| `type` | 命令或事件类型，如 prompt、get_messages、response |
| `message` | 本轮用户输入 |
| `workspace` | 平台扩展字段，选择工作目录 |
| `session` | 平台扩展字段，选择原生 Session |
| `success` | response 表示命令是否被接受 |
| `data` | 命令结果或响应数据 |

`workspace` 和 `session` 由 `pi-rpc-session` 从首条记录读取并移除，再交给 Pi；它们不是 Pi 原生命令字段，也不是模型提示词。

会话脚本进入 `/workspace/workspaces/<workspace-id>`，按 `conversation-id` 查找用户盘已有 Session：已有文件使用 `--session <确切文件>`，首次使用 `--session-id <conversation-id>`。没有 session 字段的调试连接使用 `--no-session`。

Pi 的一轮 prompt 可以产生多条文本、工具和状态事件。成功 response 表示命令被接受，不能单独用来判断整轮 Agent 工作结束；Host 等待 `agent_settled` 后才完成任务。

### 2.2.5 模型调用链路

Pi 的 Provider 配置来自数据盘的 `pi-state/agent/models.json`，Guest 中访问路径为：

```text
/home/pi/.pi/agent/models.json
```

当前 Provider 地址为 `http://<Host IP>:18082/v1`，请求链路为：

```text
Host通过8080提交prompt
    ↓
Guest Pi根据Provider配置发出模型HTTP请求
    ↓
Host Tool Gateway接收并替换Authorization凭据
    ↓
Host通过HTTPS调用DeepSeek
    ↓
模型响应经Gateway返回Pi
    ↓
Pi决定继续调用工具、再次请求模型，或结束
    ↓
Pi事件经socat/TCP返回Host Pi Gateway
```

模型要求调用工具时，Pi 先接收模型返回的工具调用意图，执行当前允许的工具，再把结果送入下一轮模型请求。当前允许的本地工具为 `read,write`，没有启用动态 MCP。

Pi RPC 的命令通道和模型 HTTP 通道各自独立。模型结果先回到 Pi 继续执行，而不是由 Tool Gateway 直接替 Pi 完成会话。

### 2.2.6 凭据隔离

默认 DeepSeek 源凭据位于运行配置用户的 Host 主目录：

```text
~/.config/ai-agent-platform/deepseek-api-key
```

启动时复制到：

```text
/var/lib/fc/control-plane/<instance-id>/sidecars/deepseek-api-key
```

副本归模型网关账户所有，权限为 `0400`。Guest 只获得 `gateway-placeholder` 和模型网关 URL。

平台登录 Cookie、模型 Key 和 Pi Session 是不同数据。登录 Cookie 证明 API 用户身份；模型 Key 用于 Host 请求供应商；Pi Session 保存 Agent 上下文。

### 2.2.7 网络限制

正式实例允许 Guest 访问本实例 Host IP 的 TCP 18082，并允许回应 Host 主动建立的连接。经 TAP 的转发流量被 nftables 阻止。

因此 Guest 不直接通过宿主机 NAT 访问外部模型，模型出站由 Host 网关执行。RPC 私网地址默认不暴露到 macOS 或公网，业务客户端通过 Control Plane HTTP API 交互。

当前参数中的 DNS 地址写入 Guest resolv.conf，不等于 Host 已经运行 DNS 代理。正式模型链路使用 Host IP，供应商域名由 Host 网关解析。

### 2.2.8 终端验收

日常业务验收使用 macOS 项目目录中的：

```bash
./agentctl login <平台用户名>
./agentctl workspace
./agentctl chat
```

如果需要观察原始 RPC，可在 Ubuntu Host 对已启动实例做独立调试。先用 `./agentctl status cli-demo` 取得真实 Guest IP，再运行例如：

```bash
nc 172.29.0.2 8080
```

发送一行：

```json
{"id":"demo-1","type":"get_state"}
```

这是原始协议调试，需在没有平台任务和历史回源读取时进行，以免占用当前唯一 RPC 连接。该记录没有平台 Session 字段，所以不会恢复业务会话。

按 Ctrl-C 断开 nc，不会停止 microVM。停止实例使用：

```bash
./agentctl stop cli-demo
```

自动验收入口分别为 `./run.sh network-lease-smoke-test`、`./run.sh agent-task-smoke-test` 和 `./run.sh cli-smoke-test`。前两者分别检查基础网络/RPC、真实任务分发；CLI smoke 覆盖认证、会话、重启和清理。

### 2.2.9 当前实现边界

当前已接入正式受管实例：动态网络租约、Workspace/Session 选择、Host Pi Gateway、统一事件和 SQLite 消息缓存。

Pi 进程仍按每条 TCP 连接启动，任务或历史回源结束后退出。退出前脚本执行 `sync`，Host 通过重新连接探测监听恢复后结束本轮任务，减少 Session 未刷盘就停止 VMM 的窗口。

当前没有常驻 Pi、Guest 进程池、动态 Skill 加载或 MCP 功能；这些不属于本次文档描述范围。

## 2.3 InstanceRuntime：实例资源与启动编排

代码位置：`services/instance-manager/runtime.py`。

`InstanceRuntime` 是 Host 上实际执行虚拟化操作的模块。Control Plane 传入实例 ID 和用户 ID，它组织磁盘、网络、模型网关、Jailer、Firecracker 与生命周期登记，再返回运行状态。它不负责 HTTP 登录和页面显示。

### 2.3.1 初始化与路径

构造时接收 `state_root`、`volume_root`、`idle_timeout_seconds`、`deepseek_credential`、`state_database` 和 `snapshot_root`。

| 参数或资源 | 默认值 |
|---|---|
| 状态根目录 | `/var/lib/fc` |
| 统一数据库 | `/var/lib/fc/control-plane.db` |
| 用户卷根目录 | `/srv/fc/volumes/users` |
| 快照根目录 | `/srv/fc/snapshots/instances` |
| 空闲阈值 | 300 秒 |
| Guest Pi RPC 端口 | 8080 |
| Host 模型网关端口 | 18082 |

`paths(instance_id, volume_owner_id)` 集中计算 jail、API Socket、数据盘、日志与快照路径。实例专属运行文件位于：

```text
/var/lib/fc/control-plane/<instance-id>/
├── console.log
├── reaper.log
└── sidecars/
    ├── gateway.log
    ├── gateway.audit.jsonl
    └── deepseek-api-key
```

文件是否存在取决于实例是否已运行，以及停止或销毁流程的清理结果。该目录保存日志与运行辅助文件；真正的用户文件在用户数据盘内。

### 2.3.2 `ensure_host()`：检查运行前提

检查当前进程为 root、内核与 rootfs 存在、Firecracker/Jailer 可执行，并创建或取得 `firecracker` 与模型网关的系统账户。

返回 VMM 和网关的 UID/GID，交给 TAP 创建、文件权限设置和子进程降权使用。这里不下载 Ubuntu、不安装 Pi，也不创建 Guest。

### 2.3.3 `create_volume()`：创建稳定用户数据盘

输入目标镜像路径和 VMM UID/GID。已有镜像直接复用；不存在时先创建 `.ext4.building`，设置 1 GiB 大小、格式化为 ext4、临时挂载并建立 `workspace`、`pi-state` 和 `pi-state/agent`。

目录在 Guest 中由 UID/GID 1001 使用，Host 镜像归 VMM 账户所有，权限 0600。同步、卸载成功后再原子替换正式文件，避免半成品被当成有效卷。

`UserVolumeStore.ensure(user_id, volume_path)` 将用户与稳定路径写入 `user_volumes`。同一用户后续不能在正常启动时被悄悄绑定到另一块盘。

### 2.3.4 `start()`：执行冷启动

接收 `instance_id`、可选 `owner_id`。正式用户传 owner_id；无属主测试可使用实例 ID 作为卷标识。

它依次调用前文说明的磁盘、网络、Gateway 和 jail 准备方法，再通过 `subprocess.Popen()` 执行 Jailer。Host 以 100 ms 间隔读取 `console.log`，最多等待 60 秒。

网络启用时，需要同时出现 `AGENT_RUNTIME_READY` 与 `PI_RPC_READY`，然后激活网络租约，通过 `lifecycle.py register` 保存 PID、进程启动时刻、网络端点、jail、磁盘路径和 sidecar PID，并派生独立 watcher。

成功返回的运行字典包括：

```text
pid / processStartTicks
apiSocket / jailPath / volumePath
hostIp / guestIp / rpcPort
tapName / nftTable / networkDatabasePath
processAlive / idleSeconds
startupTiming
```

启动失败会终止本次派生进程、尝试释放网络并清理 jail。清理仍有残留时租约保留 error，不能视为可重新分配。

### 2.3.5 停止、销毁与离线删除

`stop(instance_id)` 调用生命周期停止与清理，保留用户卷，再清除与实例关联的快照。再次启动走冷启动。

`destroy(instance_id, preserve_volume)` 删除该次实例运行元数据和临时目录。Control Plane 对有属主实例传 `preserve_volume=True`，稳定用户卷保留；无属主测试实例可以删除卷。销毁不等于删除共享 rootfs。

`delete_workspace_data(owner_id, directory_name)` 和 `delete_pi_session_data(owner_id, session_id)` 只在 Guest 停止后离线挂载用户卷，删除指定工作目录或 Session 文件，随后同步并卸载。业务对象和缓存记录由 Control Plane 另行删除。

这些文件操作不应与 Guest 可写挂载并发。快照暂停期间也应保持配对磁盘不变，先恢复或正常停止后再进行数据修改。

### 2.3.6 启动计时

`StartupTimingDiagnostic` 记录 Host 检查、磁盘、网络、Gateway、jail、Guest READY 和生命周期登记等阶段。Guest `agent-init` 输出 `GUEST_START_TIMING`，Host 将它解析到 `startupTiming`。

这些是诊断结果，不是启动条件。它们经实例响应或任务 SSE 传给 CLI，以亮粉色逐行显示，方便区分 VMM 就绪、Pi 进程启动和模型响应的耗时。

## 2.4 生命周期与运行状态存储

代码位置：

```text
services/instance-manager/lifecycle.py
services/instance-manager/runtime_store.py
```

这一层管理已经启动的 VMM 进程：确认 PID 身份、记录活动、保护忙碌任务、空闲回收和清理 Host 资源。它不处理 Pi 原生消息。

### 2.4.1 RuntimeStore 与 UserVolumeStore

`RuntimeStore` 将真实运行信息写入统一 SQLite 的 `runtime_instances`、`runtime_sidecars`；`UserVolumeStore` 将稳定用户卷绑定写入 `user_volumes`。

| 存储 | 记录内容 |
|---|---|
| `runtime_instances` | VMM PID、启动 ticks、jail、API Socket、网络、卷、停止原因 |
| `runtime_sidecars` | 本实例配套 Host 进程的 PID 与启动 ticks |
| `user_volumes` | user_id 与 volume_path 的唯一绑定 |

`RuntimeStore.save()` 在事务中保存运行记录与 sidecar 列表，`get()` 返回运行字典。旧 `/var/lib/fc/instances/<id>.json` 仅用于兼容导入，新记录写 SQLite。

业务 `instances` 表和 `runtime_instances` 不能混为一张表。前者是产品中的实例对象与状态，后者是 Host 上实际运行资源的登记。

### 2.4.2 PID 与进程身份校验

PID 是 Linux 分配的进程编号，退出后可被其他进程复用。`process_matches()` 同时检查 PID 和 `/proc/<pid>/stat` 中的启动 ticks，避免把复用 PID 的其他进程当成本实例。

这个校验用于查询、停止 VMM 和清理 sidecar，不依靠进程名猜测实例归属。

### 2.4.3 活动时间与 busy 标记

当前活动时间仍采用 Host 文件的修改时间：

```text
/var/lib/fc/activity/<instance-id>
```

busy 文件用于保护正在执行任务的实例。数据库替代了 JSON 运行记录和租约，并不意味着所有轻量运行标志都必须变成数据库字段。

Control Plane 在任务开始、执行事件和结束时调用 heartbeat；任务期间设置 busy。Tool Gateway 也会更新有效模型请求活动。查询状态、显示菜单和读取已命中的历史缓存，不会持续延长空闲计时。

### 2.4.4 `watch`：独立空闲回收

`InstanceRuntime` 通过子进程运行：

```text
lifecycle.py --state-root ... --database ... watch <instance-id> --poll-interval 1
```

watcher 每秒检查登记状态、真实进程和活动时间。busy 存在时等待；空闲达到 300 秒则停止 VMM、终止配套服务、清理网络与 jail，保留用户卷。

watcher 独立于 HTTP 服务，因此 Control Plane 退出后仍能执行回收。日志写入实例目录的 `reaper.log`。

### 2.4.5 `stop_instance()` 与异常清理

`stop_process()` 先尝试 Guest 正常退出，再根据需要使用 SIGTERM、SIGKILL；`stop_sidecars()` 清理已登记的配套进程；`cleanup_ephemeral()` 清理网络和 jail。

清理成功后将运行元数据记为 stopped，记录 stopReason、stopMethod、stoppedAt。若 VMM 意外退出，watcher 同样清理资源并记录 process_exited。

业务层 `ControlPlane.reconcile()` 在查询时根据运行信息校准业务状态。当前失活运行记录会校正为 stopped；API 启动或停止执行失败才可能写入 failed，不能统一描述为“进程退出必然进入 failed”。

## 2.5 Control Plane 与业务数据库

代码位置：`services/control-plane/server.py` 及同目录存储模块。

Control Plane 接收来自 CLI 或上层应用的 HTTP 请求，完成身份、所有权、配额和状态校验，再调用 InstanceRuntime 或 Agent Runtime。默认仅监听 `127.0.0.1:18090`。

### 2.5.1 HTTP Handler 与业务编排

`ControlPlaneHandler` 负责解析 URL、请求 JSON、Cookie，调用 `ControlPlane`，并返回 JSON 或 SSE。它将 `ApiError` 转为带 HTTP 状态码的错误响应。

`ControlPlane` 负责业务动作，例如创建实例、选择工作区、提交任务和读取历史。它通过存储对象访问数据库，通过 InstanceRuntime 操作虚拟化资源，不直接让客户端执行 Host 命令。

```text
agentctl / 上层应用
    ↓ HTTP请求与Cookie
ControlPlaneHandler
    ↓ 参数与当前用户
ControlPlane
    ├─ Store：查询和保存业务对象
    ├─ InstanceRuntime：启动/停止microVM
    └─ AgentRuntimeAdapter：执行Agent任务
```

### 2.5.2 AuthStore：用户与登录会话

代码位置：`services/control-plane/auth.py`。

`AuthStore` 在 `users` 保存用户 ID、用户名、密码随机盐和 PBKDF2-SHA256 派生值，在 `auth_sessions` 保存随机登录令牌的 SHA-256 摘要及到期时间。数据库不保存明文登录密码。

登录请求提交 username/password，认证成功后返回用户信息并设置 `aap_session` Cookie。API 使用 HttpOnly、SameSite=Strict，当前会话有效期 12 小时。登出撤销服务端会话。

当前用户由 `./run.sh configure-user` 等管理员命令创建，尚无公共自助注册接口。模型 API Key 不属于这里的登录会话表。

### 2.5.3 InstanceStore：属主、配额与业务状态

`server.py` 中的 `InstanceStore` 管理 `instances`。创建实例先保存逻辑记录，不立即分配磁盘或启动 Guest。

当前默认每个用户最多一个实例、最多运行一个。显式 `create` 可提供实例名；工作区会话流程通过 `ensure_user_instance()` 根据用户 ID 取得或创建后台实例。

Control Plane 对同实例的变更使用进程内锁，配额检查与记录更新有独立保护。它是当前单控制面进程的并发协调方式，不是分布式锁。

业务状态包括 created、starting、running、stopping、stopped、suspending、suspended、resuming、failed。数据库记录需与真实 VMM 定期或按请求核对，不能只凭数据库的 running 字符串判定进程存活。

### 2.5.4 WorkspaceStore：工作区与当前选择

代码位置：`services/control-plane/workspace_store.py`。

创建工作区接收 user_id 和 name，生成稳定 `workspace-<16位hex>`，保存到 `workspaces`；`user_workspace_preferences` 保存当前工作区。

工作区名称是显示值，磁盘目录采用稳定 ID。新建工作区先写数据库；实际任务进入 Guest 后，会话脚本才按需要创建 `/workspace/workspaces/<id>`。

切换工作区只更新当前选择，不为用户多启动一台 microVM。目录分组提供工作上下文，不是阻止同一 Pi 用户访问其他目录的操作系统级隔离。

### 2.5.5 TaskStore：会话、任务、事件和消息缓存

代码位置：`services/control-plane/task_store.py`。

| 表 | 实际用途 |
|---|---|
| `conversations` | 工作区/实例关联、Pi Session ID、标题、预览与计数 |
| `messages` | 展示用用户和 assistant 文本缓存，以及旧数据库会话历史 |
| `tasks` | 一轮请求的 prompt、状态、输出和错误 |
| `task_events` | 按 sequence 保存有序增量、工具、进度和终态事件 |
| `task_store_migrations` | 旧 tasks.db 导入标记 |

新会话 `sessionBackend=pi-native`，`piSessionId` 默认等于 conversation ID。创建任务时发送本轮用户输入，Pi 从数据盘原生 Session 恢复上下文；旧 database 会话保留受限历史拼接兼容。

`claim_next()` 使用写事务原子领取 queued 任务，将其改为 running，并追加 run.started。每实例仅有一个后台消费者，任务串行处理。

工具过程保存在 task_events；PiGateway 返回的工具结果只保留标识、错误状态和截断预览，不把所有原始结果整包写入缓存。

### 2.5.6 原生 Session 与 SQLite 历史缓存

Pi 原生 Session JSONL 是新会话的上下文权威数据，位于用户数据盘。`messages` 用于快速显示用户/assistant 文本，不代替 Pi 原生状态。

```text
打开历史
    ↓
SQLite已有缓存 → 直接返回展示内容
    ↓ 缓存为空
检查实例可用与无活动任务
    ↓
AgentRuntimeAdapter.get_messages()
    ↓
Pi从用户盘读取原生Session
    ↓
转换文本并回填SQLite
```

用户消息在提交任务时写缓存，最终 assistant 回复在 run.completed 时写入。失败请求、异常终止或外部改写原生文件可能产生差异；当前缓存命中时不逐次验证磁盘文件。

历史接口支持 limit/before 分页响应，但当前主路径先取得完整缓存再裁切；尚不能描述为数据库层严格只读取最近几十条。

缓存命中时不必启动 Pi，也不必启动已停止的 microVM。缓存缺失时的回源仍有进程启动与 Session 加载成本。处于 suspended 的实例需显式 resume，当前消息/历史回源流程不会自动把 start 转换成快照恢复。

### 2.5.7 统一数据库与查看方式

当前统一使用：

```text
/var/lib/fc/control-plane.db
```

各 Store 共享文件，但分别负责自己的表和事务。WAL 模式运行时可能出现 `-wal`、`-shm` 辅助文件。数据文件、原生 Session、rootfs、模型 Key 和快照正文不写进这些业务表。

旧 `/var/lib/fc/tasks/tasks.db` 只用于一次性迁移。下面是 Ubuntu Host 只读查询示例，不要求另装 sqlite3 命令行工具：

```bash
sudo python3 -c 'import sqlite3; db=sqlite3.connect("file:/var/lib/fc/control-plane.db?mode=ro",uri=True); print(db.execute("SELECT name FROM sqlite_master WHERE type=? ORDER BY name",("table",)).fetchall()); db.close()'
```

检查单表结构可使用 sqlite3 模块执行 `PRAGMA table_info(network_leases)`。后续程序应通过 Store 方法更新数据，不手工修改运行实例的关联行。

## 2.6 Agent Runtime Adapter 与 Host Pi Gateway

代码位置：

```text
services/agent-runtime/agent_runtime.py
services/pi-gateway/gateway.py
```

这一层处理“平台要 Agent 做什么”和“Pi RPC 具体怎么表达”的对应关系。它使用已启动实例的 Guest IP，不创建 microVM，也不直接操作数据库。

### 2.6.1 AgentRuntimeAdapter：平台接口

当前接口包含两个动作：

```text
execute(host, port, prompt, on_event, workspace_id=None, session_id=None) -> str
get_messages(host, port, workspace_id, session_id) -> list[dict]
```

| 参数 | 来源和作用 |
|---|---|
| host / port | InstanceRuntime 运行记录中的 guestIp / rpcPort |
| prompt | TaskStore 中本轮任务输入 |
| on_event | Control Plane 提供的事件保存回调 |
| workspace_id | Conversation 所属工作区 |
| session_id | Conversation 对应的 Pi Session ID |

`execute()` 返回最终文本，执行过程中通过回调返回增量和工具事件；`get_messages()` 返回原生消息列表，用于缓存回源。

当前实现 `PiRuntimeAdapter` 包装 PiGateway，并将 `PiGatewayError` 转换为 `AgentRuntimeError`。尚未将健康检查、Session 删除或多 Agent 动态选择纳入接口；Session 删除目前由 InstanceRuntime 的离线盘操作完成。

### 2.6.2 PiGateway：连接与命令发送

`PiGateway` 保存连接和任务超时配置，每次 execute/get_messages 新建 TCP 连接。默认连接重试窗口 10 秒，任务超时 240 秒。

它用 socket 的 reader/writer 按行发送和读取 JSONL。每条记录设有 4 MiB 大小上限，非法 UTF-8、非法 JSON、超时或提前断线会转换成运行错误。

任务命令加入 workspace/session 扩展字段，由 Guest 会话脚本处理。协议操作只发生在当前连接中，PiGateway 对象不保存某个用户的活动会话状态。

### 2.6.3 原生事件转换

| Pi 原生事件 | 平台事件 | 作用 |
|---|---|---|
| agent_start | progress，stage=model_started | 提示执行已开始 |
| message_update / text_delta | message.delta | 立即返回文本增量 |
| tool_execution_start | tool.started | 保存工具名、调用 ID 和参数 |
| tool_execution_end | tool.completed | 保存错误状态和结果预览 |
| auto_retry_start | progress，stage=retrying | 返回重试次数和延迟 |
| message_end | 暂存在 Gateway 内 | 提取最终 assistant 文本 |
| agent_settled | 允许 execute 返回 | 确认本轮 Agent 已结束 |

工具结果预览最多保留 2000 字符。`message_end` 不是整轮任务完成标志，因为之后还可能发生工具调用、模型重试或下一轮输出。

`run.started` 由 TaskStore 领取任务时创建；`run.completed` 和 `run.failed` 由 Control Plane 在 execute 返回或异常后追加，不是 Pi 原生事件名。

### 2.6.4 结果怎样写入数据库并返回客户端

Control Plane 调用 execute 时提供 `save_event(event_type, payload)`。PiGateway 每解析出一条平台事件，就调用这个函数；函数内部通过 `TaskStore.append_event()` 写 SQLite，并按节流规则更新活动时间。

任务完成后，Control Plane 追加 run.completed、更新 task 终态和 assistant 消息缓存。HTTP SSE handler 从 task_events 读取有序事件推送客户端，而不是让 PiGateway 直接写网页或终端。

```text
Pi原生事件
    ↓ PiGateway解析和转换
on_event回调
    ↓ Control Plane
TaskStore.append_event()
    ↓ SQLite task_events
SSE handler
    ↓ HTTP事件流
agentctl / 上层客户端
```

SSE 帧包含 sequence/id，支持 Last-Event-ID 或 after 游标续传，10 秒发送注释心跳。终态事件后服务端结束流；客户端应据终态结束订阅。

## 2.7 Tool Gateway：模型代理与凭据隔离

代码位置：`services/tool-gateway/gateway.py`。

Tool Gateway 是每实例配套的 Host 模型 HTTP 代理。它与 PiGateway 名称相近，但职责不同：PiGateway 控制 Agent，Tool Gateway 转发 Agent 发出的模型请求。

### 2.7.1 输入与启动

`InstanceRuntime.start_model_gateway()` 通过 `setpriv` 切换到专用网关 UID/GID，并传入：

| 参数 | 含义 |
|---|---|
| listen-host / listen-port | 本实例 Host TAP IP 与 18082 |
| upstream | 当前为 `https://api.deepseek.com` |
| credential-file | Host 上权限 0400 的临时凭据副本 |
| audit-file | gateway.audit.jsonl |
| activity-file | 当前实例活动时间文件 |
| tenant | 当前传实例 ID，作为审计标识 |

这里的 tenant 参数名不是已实现完整多租户管理体系的证明。

### 2.7.2 请求处理与输出

当前只代理 `POST /v1/chat/completions`，检查请求 JSON 和大小，丢弃 Guest 自带 Authorization，再注入 Host 文件中的真实 Bearer Key。

普通响应返回 JSON；流式模型响应逐块转发 SSE，不等待全文完成。上游失败转换为代理错误响应，Pi 再处理该错误或按其策略重试。

网关的 SSE 是“模型 → Pi”的响应流；Control Plane 的 SSE 是“任务事件 → CLI”的业务事件流。两者的数据格式和接收方不同。

### 2.7.3 日志与访问边界

网关日志和脱敏审计在实例 sidecars 目录。审计记录状态、耗时、字节量等元数据，不记录 Authorization 或完整请求正文。

Guest 占位 Key 本身不是业务用户认证凭据；当前访问边界主要依靠独立 TAP 地址、网络规则和 Host 监听范围。模型网关没有对外提供公共用户登录接口，也没有实现当前暂缓的 MCP 网关功能。

## 2.8 Firecracker 快照暂停与恢复

主要代码位于 `InstanceRuntime.suspend()`、`resume()`，API 层位于 `ControlPlane.suspend()`、`resume()`。

快照是 Firecracker 的原生 VMM 能力，平台负责状态、文件配对、网络重建与操作顺序。它用于恢复同一个用户实例，不是通用预热池。

### 2.8.1 暂停前的业务检查

用户通过 `./agentctl suspend <instance-id>` 发出请求。Control Plane 校验所有权、运行状态以及是否存在活动任务，将业务状态转为 suspending，再调用 InstanceRuntime。

任务忙碌时不能直接保存为可继续工作的空闲快照。整个过程需要与同实例的任务和生命周期变更协调。

### 2.8.2 保存哪些文件

```text
/srv/fc/snapshots/instances/<instance-id>/
├── memory.snap
├── vmstate.snap
└── manifest.json
```

| 文件 | 当前保存内容 |
|---|---|
| memory.snap | Guest RAM，包括进程内存、内核内存和可能尚在缓存中的文件数据 |
| vmstate.snap | vCPU、虚拟设备及 VMM 恢复所需状态 |
| manifest.json | 实例/用户 ID、创建时间、rootfs Build ID、用户卷路径和原网络租约 |

rootfs 和用户数据盘仍作为 Host 上独立镜像存在。内存中的缓存不等于完整数据盘副本，恢复必须继续提供同一配对磁盘状态。

### 2.8.3 `suspend()`：生成快照并释放资源

核心步骤为：

```text
标记busy，防止空闲回收干扰
    ↓
PATCH /vm，state=Paused
    ↓
PUT /snapshot/create，生成Full快照
    ↓
将快照移出待清理jail
    ↓
停止VMM但跳过Guest正常关机
    ↓
清理sidecar、TAP、nftables和jail
    ↓
保存manifest，状态变为suspended
```

保存期间业务状态为 suspending；完整成功后才进入 suspended。Guest 停止执行后，Host 释放 VMM 进程及其内存占用，快照文件继续占磁盘空间。

暂停后的用户卷不能被另一个实例继续写入，否则旧内存快照与磁盘内容可能不再一致。当前依靠业务所有权、单用户单实例及生命周期流程约束，没有实现跨服务器的卷租约服务。

### 2.8.4 `resume()`：重新创建 Host 资源

恢复首先验证 manifest 中的用户、实例、rootfs Build ID 和数据盘路径，并确认快照文件存在。这是兼容性与配对检查，不是对数据盘全文做内容哈希校验。

之后重新预留原 slot、创建相同 TAP/IP/MAC 与防火墙、启动模型网关，在新 jail 内链接系统盘、数据盘及两份快照，再启动带 API Socket 的空 Firecracker：

```text
PUT /snapshot/load，resume_vm=false
    ↓
PATCH /vm，state=Resumed
    ↓
激活网络租约
    ↓
登记新的VMM/sidecar PID，启动watcher
    ↓
业务状态返回running
```

Guest 的 IP/MAC 和内核挂载状态来自原快照；Host VMM PID、API Socket 和 TCP 连接需要重新创建。旧 TCP 连接不能按原样继续使用。

### 2.8.5 当前恢复指标与使用边界

`resumeTiming` 包括模型网关启动、VMM API 就绪、快照加载、恢复调用和总耗时。该总耗时表示平台恢复步骤完成，不包含随后新启动 Pi 并加载 Session，不能直接当成“用户看到模型答案”的时间。

当前快照没有自动到期删除策略。正常 stop/destroy 会丢弃关联快照；暂停后不再操作时，不能把 300 秒空闲阈值理解为快照 TTL。

恢复需要原网络槽位可用、系统盘 Build ID 匹配、用户卷保持配对。当前没有自动换址修复、跨 Host 迁移或失败后无条件回退冷启动。

## 2.9 agentctl：最小终端客户端

入口位于仓库根目录 `agentctl`，实际逻辑在 `services/cli/main.py`。它在用户发起命令的系统上运行；当前主要验收环境为 macOS。

### 2.9.1 API 连接与 SSH 隧道

CLI 默认请求 `http://127.0.0.1:18090`，不直接读取 Host 数据库或连接 Guest 8080。

macOS 开发环境由 `./run.sh tunnel` 建立：

```text
macOS 127.0.0.1:18090
    ↓ SSH端口转发
Ubuntu Host 127.0.0.1:18090
    ↓ Control Plane
实例管理 / Agent Runtime
```

隧道终端保持等待表示转发持续运行，不是日志监控面板。Ctrl-C 关闭隧道，只影响客户端连接，不等于停止 microVM。

### 2.9.2 登录状态保存

`SessionStore` 将 Cookie、用户信息、服务地址及启动计时基线保存在：

```text
~/.config/ai-agent-platform/agentctl-session.json
```

文件权限为 0600。它保存在 CLI 所在机器，与 Guest 数据盘无关。停止或重建 microVM 不会清除平台登录；logout 会撤销服务端会话并清理本地状态。

该小 JSON 文件保存客户端配置，和已经迁移到 SQLite 的网络租约不是同一用途。

### 2.9.3 工作区与会话菜单

`./agentctl workspace` 列出当前用户工作区，提供 New、打开/选择、删除等操作。`./agentctl chat` 显示当前工作区的会话菜单，并提供创建、打开、删除。

菜单按活动时间显示，时间使用 `MM/DD HH:mm`，消息预览正文截取前 10 个字符，超长时追加省略号，配合不同颜色区分名称、日期和预览。当前菜单最多展示前 20 个会话。

注意两种入口行为不同：

```text
./agentctl chat
    → 选择当前工作区下的会话

./agentctl chat cli-demo
    → 未指定 --conversation 时直接创建实例级新会话
```

继续确切会话可用 `./agentctl chat cli-demo --conversation <conversation-id>`。这些 ID 来自 API 对象，不是镜像文件名。

### 2.9.4 聊天输入与结果显示

CLI 接收用户文本，POST 到 conversation messages 接口，取得 taskId 后订阅任务 SSE。message.delta 逐段显示，tool 事件显示工具过程，终态结束本轮输入等待。

新会话创建本身不启动实例，第一条消息才按需启动。打开旧会话先读取展示历史，缓存命中可在实例停止时完成。/exit 和 /quit 退出 CLI 对话，不停止实例；普通 exit 文本会作为用户消息发给 Pi。

当前对话内没有直接切换工作区的快捷命令，需要退出后重新使用 workspace/chat 菜单。

### 2.9.5 删除、停止与销毁

| 操作 | 当前效果 |
|---|---|
| 菜单删除会话 | 调用 DELETE API，检查任务并清理对应 Session 与元数据 |
| 菜单删除工作区 | 调用 DELETE API，清理该工作区文件、会话及关系 |
| `agentctl stop <id>` | 停止计算，保留业务记录和用户数据盘 |
| `agentctl suspend <id>` | 保存快照并暂停 |
| `agentctl resume <id>` | 显式恢复暂停实例 |
| `agentctl destroy <id>` | 删除实例与关联业务记录；有属主的稳定用户卷保留 |

销毁提示需结合当前后端语义理解，不应直接把 destroy 等同于“删除用户账号及全部持久数据”。正式用户卷仍由 user_volumes 绑定。

### 2.9.6 API 作为上层接入边界

CLI 使用登录、工作区、Conversation、消息、任务 SSE 和实例管理 HTTP 接口。上层前后端可复用这些接口，不需要实现 nc、socat 或 Firecracker 调用。

字段、错误码和响应以 `docs/api/API契约.md`、`docs/api/openapi.yaml` 及当前 server.py 为准。终端颜色、光标和菜单是 CLI 展示逻辑，不属于 Agent Runtime 或数据库协议。
