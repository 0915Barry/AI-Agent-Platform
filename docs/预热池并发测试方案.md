# 预热池并发测试方案

> 实施状态：场景 A、B、C 已完成，并于 2026-11-19 通过真实 Firecracker 验收。
> 小规模 `3/1/1`、多轮 `5/2/3` 和较高负载 `8/2/5` 均通过，未发现重复领取、
> 同卷双写或网络资源残留。

## 1. 目标

本模块验证多个真实用户同时通过 Control Plane 启动实例时，预热池的原子领取、
数据盘独占、冷启动回退和 Worker 补池逻辑仍然正确。该测试先关注正确性，不以压满
CPU、内存或最大吞吐量为目标。

核心问题是：

- 一台 `ready` 预热机是否永远只能被一个启动请求领取；
- 预热机数量少于并发用户时，其余请求是否立即冷启动；
- 不同用户数据盘是否始终只绑定自己的 Runtime；
- Worker 补池、用户停止和 Runtime 清理同时发生时，是否会遗留资源；
- 同一逻辑实例的重复并发 START 是否被实例锁和状态机正确拒绝。

## 2. 测试定位

项目已有三类相关验证：

| 已有测试 | 已验证内容 | 未覆盖内容 |
|---|---|---|
| SQLite 并发领取单测 | 8 个线程争抢 1 条 ready 记录，只有 1 个成功 | 真实 Firecracker、网络和数据盘 |
| Control Plane 配额并发单测 | 同一用户的并发启动只有 1 个成功 | 多用户预热争抢 |
| `prewarm-pressure-test 100` | 串行领取、停止和补位 100 轮无泄漏 | 同一时刻的多请求竞态 |

新模块使用真实 Control Plane、Worker、Firecracker、TAP、nftables 和 ext4 数据盘，
补齐“真实全链路多用户并发”这一空缺。

## 3. 模块与文件

| 文件 | 职责 |
|---|---|
| `scripts/linux/prewarm-concurrency-smoke.py` | 创建用户、同步释放并发请求、抓取状态并判定结果 |
| `scripts/linux/prewarm-concurrency-smoke-test.sh` | 环境检查、测试锁、独立目录和最终清理 |
| `run.sh prewarm-concurrency-test [users] [ready] [rounds]` | macOS 统一入口，同步仓库并在 Ubuntu Host 执行 |

命令默认参数为：

```text
users=3
ready=1
rounds=1
```

该组合用于快速冒烟；正式多轮验收使用 `users=5 ready=2 rounds=3`。参数必须满足
`users >= 2`、`ready >= 1`、`users > ready`。

## 4. 隔离边界

测试使用独立资源：

```text
状态目录  /var/lib/fc/prewarm-concurrency
结果目录  /var/lib/fc/prewarm-concurrency-results
数据库      /var/lib/fc/prewarm-concurrency/control-plane.db
Control Plane 端口  18099
Worker 锁    /run/ai-agent-prewarm-concurrency.lock
测试锁      /run/ai-agent-prewarm-concurrency-test.lock
```

测试必须拒绝与长期 Control Plane、Worker 或其他预热测试共享数据库和锁。每个用户
使用独立 CookieJar、逻辑实例 ID 和持久数据盘。测试不发送真实模型请求。

## 5. 场景 A：确定性的有限池争抢

该场景用于精确证明“2 台 ready 只能产生 2 次预热命中”。为避免 Worker 在并发请求
进入前又补出新机，测试步骤为：

1. 启动 Worker，等待池中恰好出现 `ready` 台预热机；
2. 记录这些 Runtime ID、PID、进程代次和网络槽位；
3. 安全停止 Worker，保留已就绪的预热机；
4. 使用 `threading.Barrier` 同时释放所有用户的 `POST /start`；
5. 等待全部请求完成，再执行一致数据库快照和宿主资源快照。

通过条件：

- 成功启动数等于 `users`；
- `strategy=prewarm` 的数量等于初始 `ready` 数；
- 预热响应中的 Runtime ID 两两不同，且必须属于初始 ready 集合；
- 其余请求的实际策略均为 `cold`，不出现等待补池后再命中；
- 所有实例的 Runtime ID、PID、网络子网、TAP 和 nftables 名称不重复；
- 每条 attachment 的用户、逻辑实例、Runtime 和数据盘必须与请求一致；
- 任一数据盘最多只有 1 条非终态 attachment。

## 6. 场景 B：同一实例重复 START

对同一用户、同一逻辑实例同时发送 2 个 START：

- 只允许 1 个请求成功；
- 另 1 个必须返回可预期的 `instance_busy` 或 `instance_running`；
- 不能多消耗预热机；
- 不能创建第二条 attachment、binding 或网络租约；
- 最终业务状态必须为 `running`。

## 7. 场景 C：Worker 在线补池与并发停止

场景 A 通过后重启 Worker，连续执行 `rounds` 轮混合操作：

1. 同时启动多个用户实例；
2. Worker 在后台计算缺额并补建预热机；
3. 实例全部 `running` 后，同时发送 STOP；
4. 等待补池恢复 `target_ready`；
5. 核对数据库与宿主资源，然后进入下一轮。

该场景不强制每轮精确命中数，因为 Worker 补池和请求到达时序是真实竞态；但必须满足：

- 没有两个启动结果指向同一物理 Runtime；
- 没有两个活动 attachment 指向同一数据盘；
- 请求不因等待 `preparing` 超过冷启动的合理上界；
- STOP 完成后不留 `claiming/assigned`、binding 或 attachment；
- 已退役预热 Runtime 的 Firecracker、TAP、nftables、Jailer 和占位盘全部清理；
- Worker 最终恢复且不突破 `target_ready/max_total`。

## 8. 并发器设计

测试客户端使用 `concurrent.futures.ThreadPoolExecutor`，每个用户持有自己的 HTTP opener 和 CookieJar。
任务先在 `threading.Barrier(users + 1)` 上等待，主线程确认全部工作线程就绪后一次释放。

每个请求结果保存：

```text
userId / instanceId / requestedAt / completedAt / latencyMs
HTTP status / error code / actual strategy / runtimeId
operationId / activationId / volumePath
```

线程不直接写共享 JSONL；先返回结构化结果，由主线程统一排序和落盘。

## 9. 一致快照与失败诊断

在关键断言前，使用一个 SQLite 读事务同时抓取：

```text
instances
runtime_bindings
runtime_instances
runtime_sidecars
prewarm_items
volume_attachments
startup_operations
network_leases
```

失败时先在 Control Plane、Worker 和 Firecracker 仍运行时执行只读现场采集，
终端立即输出负载、CPU/IO/memory PSI、可用内存和活动 VMM 数量摘要。采集完成后
再停止 Control Plane 和 Worker，并使用 SQLite backup API 归档数据库。归档同时保存：

- 所有并发请求的原始结果；
- Control Plane 与 Worker 日志；
- Firecracker、Jailer、gateway、watcher 进程列表；
- TAP、路由、nftables 和网络租约；
- 采集时的 loadavg、vmstat、CPU/I/O/memory PSI、`/proc/meminfo` 和磁盘状态；
- 各运行时表的记录数与状态分布；
- 每台 Guest 最后 256 KiB 串口日志；
- 失败断言、场景、轮次和时间戳。

归档完成后仍必须执行全局 Runtime 兜底清理，诊断不得造成资源泄漏。

## 10. 超时与判定

- 单次 START 最长 90 秒，单次 STOP 最长 30 秒；
- 并发任务必须全部结束，不得忽略 future 异常；
- 场景 A 要求精确的 `prewarm=ready`、`cold=users-ready`；
- 场景 B 要求恰好 1 个成功，其余为可预期 409；
- 场景 C 要求所有轮次均通过状态和资源不变量；
- 任意 HTTP 500、数据盘重复绑定、Runtime 重复领取或资源清理失败均立即终止。

当前成功输出为：

```text
PREWARM_CONCURRENCY_SCENARIO name=finite-pool round=1/3 users=5 prewarm=2 cold=3 status=pass
PREWARM_CONCURRENCY_SCENARIO name=duplicate-start success=1 rejected=1 status=pass
PREWARM_CONCURRENCY_SCENARIO name=live-worker round=1/3 users=5 prewarm=2 cold=3 pool=replenished status=pass
PASS: real prewarm concurrency invariants remained valid
PREWARM_CONCURRENCY_READY users=5 ready=2 rounds=3 unique=verified duplicate_start=verified live_worker=verified volume=exclusive network=clean pool=replenished
```

## 12. 实际验收结果

`5/2/3` 验收包含 3 轮有限池争抢、1 次重复 START 和 3 轮 Worker 在线补池：

- 场景 A 每轮精确产生 2 个预热命中和 3 个冷启动；
- 场景 B 精确产生 1 个成功和 1 个 HTTP 409 拒绝；
- 场景 C 每轮停止后均恢复 2 台 `ready` 预热机；
- Runtime、PID、数据盘、子网、TAP 和 nftables 名称没有重复；
- 测试结束后 binding、attachment、网络租约、Jailer 和占位盘均完成清理。

更高规模测试得到以下开发环境容量结果：

- `7/2/5` 与 `8/2/5` 均完成 5 轮有限池争抢、1 次重复 START 和 5 轮 Worker 在线补池，
  所有状态、独占与清理不变量均通过；
- `10/3/5` 两次未通过：早期在 Worker 在线第 2 轮超时，启用 Host 探针后
  在有限池第 4 轮超时；
- 早期 `8/2/3` 在 Worker 在线第 3 轮出现同类超时，但后续 `8/2/5` 全部通过；
- 各次失败前已完成的有限池争抢、重复 START 或 Worker 在线轮次均通过；
- 最新失败时 loadavg 为 `9.38/5.20/3.61`，CPU PSI `some avg10=76.81`，而 I/O PSI 和
  memory PSI 均为 `0.00`，可用内存仍约 7.1 GiB；
- 失败 Guest 的 `kernel_to_init` 增长到约 34～42 秒，数据盘挂载增长到约 8～10 秒，
  与正常约 3 秒和 0.1 秒相比，已有直接证据指向 Host CPU 调度饱和；
- 当前没有证据表明失败来自重复领取、同卷双写或网络租约冲突。

因此 `8/2/5` 是当前 Apple Silicon + UTM 开发环境已经验证的较高负载基线，
但不能把单次通过直接外推为生产服务器容量。同一规模早期曾失败、本次更多轮次通过，
表明边界受 UTM 当时的 Host 调度状态影响，不是简单的固定用户数阈值。
`10/3/5` 已两次进入 CPU 饱和并触发 Guest 就绪超时，开发机容量探测到此结束，
不再通过增加超时或重试掩盖超载。

## 13. 非目标

本阶段不测试真实模型 API、外网首字延迟、快照恢复、跨服务器调度、对象存储下载和生产
灰度。这些能力不得混入本轮并发正确性的通过标准。
