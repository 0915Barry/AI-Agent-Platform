# **企业智能体平台技术架构**



## **一、设计目标与约束**

|维度|目标|
|---|---|
|多租户|支持独立用户/团队隔离,会话、记忆、文件、凭据互不可见|
|并发|单实例支持数百级并发会话,水平扩展到万级|
|会话连续性|长会话可中断、可恢复、可回放|
|Agent 多样性|一个平台可挂载多个不同角色/配置的 Agent|
|可运营|计量、计费、配额、审计、灰度上线|
|安全|凭据不落明文、工具调用受控、数据可合规导出/删除|

关键约束：核心Agent（框架或者应用）若是单进程单会话模型，平台层必须解决"一个 Agent 运行时如何被多个并发请求复用或隔离"这一核心问题，这是整份方案的题眼。

## **三、多租户与用户模型**

### **3\.1 租户层级**

Platform ──► Tenant\(组织/团队\) ──► User ──► Agent实例\(每个用户可拥有多个\)

Tenant 是计费、配额、配额隔离的边界；个人用户也视作一个 size=1 的 Tenant。

User 是登录主体，归属一个或多个 Tenant。

Agent 实例 是用户在平台创建的、绑定了特定角色/Prompt/工具集/模型的 Agent 配置 \+ 运行态。

如果不是多租户模式（互联网SaaS服务），而是在公司内部部署，那么每个 Tenant 就对应一个公司内部的用户/团队。每个 User 就对应一个公司内部的员工。

每个 Agent 实例 就对应一个公司内部的智能体。

每个会话 就对应一个公司内部的会话。

每个记忆 就对应一个公司内部的记忆。

每个文件 就对应一个公司内部的文件。

每个凭据 就对应一个公司内部的凭据。



### **3\.2 数据隔离策略**

三选一，按规模递进:

|方案|实现|适用|
|---|---|---|
|行级隔离|所有表加 tenant\_id \+ 应用层强制注入查询条件|起步阶段,最快|
|Schema 隔离|每个 Tenant 独立 PG Schema|中型,合规要求中等|
|库隔离|大客户独立 DB/实例|企业大客户、强合规|

起步建议：行级隔离 \+ 应用层通过 ORM 的全局 Filter\(如 Hibernate @Filter、MySQL 的 tenant interceptor\)强制注入 tenant\_id,避免任何一条 SQL 漏判。所有对象存储 key 前缀也带 tenantId/userId/agentId/\.\.\.。



### **3\.3 用户/租户表结构\(关键表\)**

tenants\(id, name, plan, quota\_json, created\_at\)

users\(id, tenant\_id, email, role, status\)

agents\(id, tenant\_id, owner\_user\_id, name, template\_id, config\_json, status\)

sessions\(id, tenant\_id, user\_id, agent\_id, title, status, created\_at, updated\_at\)

messages\(id, session\_id, role, content, tokens\_in, tokens\_out, tool\_calls\_json, created\_at\)

files\(id, tenant\_id, owner\_id, object\_key, mime, size, sha256\)

credentials\(id, tenant\_id, scope, enc\_ref\)        \-\- 仅存密文引用

usage\_events\(id, tenant\_id, user\_id, agent\_id, type, amount, ts\)

config\_json 里放该 Agent 的 system prompt、绑定的工具列表、模型选择、温度等——这是 Pi Agent 实例启动的入参。

### **4\.2 Worker 池模型**

Agent 实例本身的状态性，决定了 Worker 的两种形态：

若 Agent 可无状态化\(每次调用传入完整上下文即可运行\)：用 无状态 Worker 池，类似 HTTP 服务，K8s Deployment 水平扩缩。每次请求从 Redis/PG 拉上下文 → 喂给 Agent → 写回。首选。

若 Agent 有进程内状态\(如加载到内存的长期记忆、本地缓存\)：用 有状态 Worker 池，一个 session 绑定一个 worker，通过一致性哈希路由； worker 崩溃后从持久化的 checkpoint 重建。

平台层统一封装一个 AgentRunner 接口, 屏蔽两种形态差异

```Python
class AgentRunner:
    async def invoke(self, agent_id, session_id, user_msg, ctx) -> AsyncIterator[Event]: ...
    async def cancel(self, session_id): ...
    async def checkpoint(self, session_id): ...
```



### **4\.3 上下文管理**

长会话上下文爆炸是平台必踩的坑。三层策略:

近期窗口：最近 N 条消息常驻，直接喂给 Agent。

滚动摘要：超出窗口的消息调用小模型做分段摘要，存摘要不存原文。

向量召回：对历史消息建索引，按当前问题语义召回相关片段补进上下文。

记忆与对话分离存储：对话流水进 PG/ClickHouse\(便于回放、审计\)，语义记忆进向量库\(PGVector / Milvus / Qdrant\)。



### **4\.4 长任务与异步**

Agent 一次执行可能几十秒到几分钟\(工具调用、子任务\)。接入层不能同步等。

客户端用 SSE / WebSocket 接收流式事件\(token、工具调用、思考过程\)。

超长任务\(\>阈值\)切到 异步模式：返回 task\_id,Worker 在后台跑，完成后 webhook 回调或客户端轮询。

所有进行中任务写入 MQ\(Redis Stream / Kafka\)，Worker 崩溃后由另一个 Worker 接力重放，保证 at\-least\-once。



## **五、工具调用与沙箱**

多用户平台里，Agent 调用工具是最危险的面——一个用户让 Agent 执行代码或访问 URL，绝不能影响另一个用户或宿主机。

### **5\.1 工具网关\(Tool Gateway\)**

所有工具调用必须经统一网关，不允许 Agent 直连外部:

Agent ──► ToolGateway  ──► 鉴权\(该用户/租户能否用此工具\)

──► 配额检查

──► 参数 schema 校验

──► 执行\(本地内置 / 远程 MCP / 外部 API\)

──► 审计落盘

──► 返回\(脱敏后\)



### **5\.2 沙箱**

Agent 运行在沙箱环境，隔离宿主机和其他 Agent:

沙箱也是智能体平台最为核心的模块，负责隔离和保护 Agent 运行环境，防止恶意代码或外部攻击。

对于沙箱的技术选型，需要单独做评估说明。

按工具风险分级:

|工具类型|沙箱方式|
|---|---|
|代码执行|每次请求起独立容器 / MicroVM\(Firecracker、gVisor\)，CPU/内存/磁盘/网络配额，结束即销毁|
|文件读写|仅限该用户命名空间下的对象存储前缀,路径校验防穿越|
|网络请求|出站域名白名单，禁内网，带每会话 QPS/流量上限|
|DB 查询|只读账号 \+ 行级权限 \+ 查询超时|

## **六、凭据与密钥管理（重要，但自研公司使用可以不在一期实现）**

用户给 Agent 配的工具\(自己的 GitHub Token、数据库密码、API Key\)是高危资产。

绝不明文存库，也不建议平台自己加密存在应用 DB。

接入专业密钥服务：HashiCorp Vault / AWS Secrets Manager / KMS。平台只存一个 credential\_ref，运行时由 Worker 用租户隔离的 IAM 身份去 Vault 取，取完仅在内存，用完即焚，不写日志、不进 trace。

日志和审计里，凡是涉及凭据的字段一律 mask，只记"用了哪个 credential\_id，调了哪个工具"。



## **七、模型与 Agent 模板**

### **7\.1 模型路由**

平台后接多家模型供应商，前端让用户选或由 Agent 模板固定。路由层负责:

按租户套餐决定可用模型白名单;

按成本/延迟/质量做 fallback\(主模型超时降级到备模型\);

统一 token 计量，不同厂商口径归一。

可通过NewAPI这类模型聚合网关服务进行统一配置，实现模型的动态切换和负载均衡。

并让终端用户统一模型调用和计费，无需关心底层模型的差异。也只需要与NewAPI通过后台的方式进行API key的管理。



### **7\.2 Agent 模板市场**

agent\_template 表沉淀可复用的 Agent 形态\(如"客服 Agent""数据分析 Agent""代码助手"\)。用户从模板一键创建自己的 Agent 实例，再改 prompt/工具/模型。模板支持版本化，平台可灰度推送模板更新。

这是平台的核心功能，也是用户最常使用的功能。不同部门岗位的用户，需要根据自己的场景，选择不同的 Agent 模板。当然，前期平台是需要与终端用户进行AI Agent应用开发协作的。先让先行者从实际工作中完成AI应用开发部署，再从运行中进行模版化。从而完成普通用户的推广落地。



## **八、核心Agent组件选型**

### **8\.1 现有Agent还是自研Agent**

目前市场上比较成熟的Agent有OpenClaw、Hermes Agent、OpenCode这类功能比较全，完全定位于个人智能助理的开源项目。

也有轻量点的如OpenClaw的内核Pi Agent，DeepSeek Harness这类功能极简，需要做很多定制化配置的Agent。

也有纯粹为开发框架类的如Agent Scope（阿里巴巴），LangGraph，ADK（google），Eino（字节跳动）需要做大量定制化开发的Agent。

从企业智能体平台的角度看，这些Agent都可以作为平台的组件，被用户调用。但是，不同的Agent有不同的功能和性能，要根据自身需要进行评估选择。

从技术选型的角度看，这些Agent都有自己的优势和劣势。

|复杂度|Agent|优势|劣势|
|---|---|---|---|
|高|OpenClaw、Hermes Agent、OpenCode|功能全，开箱即用，开发量少|配置复杂，自定义复杂度交给了使用者。平台运行多用户环境，隔离成本非常高|
|中|DeepSeek Harness|功能极简，沙箱环境运行资源适中|配置简单，开发量小，但是功能简单，需要用户自己实现很多功能|
|中|Agent Scope、LangGraph、ADK、Eino|功能复杂，适应性最强，运行资源可控|开发量大，把 Agent 主要的能力都交给了 Agent 开发者；要实现外部开源成熟 Agent 的水平，对研发部门的要求较高，落地时间会不可控|



## **附录一**

### **沙箱底层技术调研**

#### **一、什么是 microVM**

microVM 是一种极简虚拟机：用标准硬件虚拟化\(KVM\)提供完整 OS 级隔离，但只模拟最少设备\(virtio 网卡/块设备/串口\)，去掉图形、USB、PCI 等臃肿外设。结果是：

|指标|microVM\(Firecracker\)|普通 VM\(QEMU\)|容器\(Docker\)|
|---|---|---|---|
|隔离强度|硬件级\(独立内核\)|硬件级|共享内核\(弱\)|
|启动时间|\~125ms|数秒\~数十秒|\~百ms|
|内存开销|\~5MB 起步|数百 MB|\~10MB|
|单机密度|数千实例|数十|数百|
|攻击面|极小\(最少设备模拟\)|大\(全设备模拟\)|共享内核,逃逸风险|

一句话：microVM = 容器的速度与密度 \+ VM 的隔离强度。这正是 Agent 多用户平台需要的——每个用户一个 microVM，跨用户硬件级隔离，同时能快速拉起/恢复。



#### **二、主流 microVM 技术对比**

|方案|出品|核心机制|适合场景|
|---|---|---|---|
|Firecracker|AWS|KVM \+ 最小设备模拟 \+ jailer 沙箱 \+ seccomp|高密度多租户、Serverless\(AWS Lambda/Fargate 底座\)|
|Cloud Hypervisor|Intel/裸机|KVM,比 Firecracker 设备更全\(支持 PCI、热插拔、VFIO\)，仍轻量|需要更多设备支持\(如 GPU/大内存\)的工作负载|
|gVisor|Google|非 VM，用户态内核\(Sentry\)拦截系统调用，ptrace 或 KVM 平台|容器级部署、不想跑完整 VM 但要强于 namespace 的隔离|
|Kata Containers|OpenStack|QEMU/Cloud Hypervisor 跑容器，容器接口 \+ VM 隔离|已有 K8s 环境、想给容器加 VM 隔离|

**2\.1 Firecracker 架构\(推荐方案\)**

Firecracker 是本方案首选，重点讲:

┌──────────────────────────────────────────┐

│  Host\(你的服务器,需 Linux \+ KVM\)                                            │

│                                                                                             │

│  ┌─────────────┐              ┌─────────────────┐  │

│  │ firecracker             │              │  jailer                            │  │

│  │  进程\(VMM\)           │◄───     │  \(沙箱封装\)                   │  │

│  │                            │              │  \- chroot命名空间            │  │

│  │  KVM                    │              │  \- cgroups资源                │  │

│  │  ┌────────┐    │              │  \- seccomp过滤               │  │

│  │  │ Guest         │    │              │  \- drop权限                    │  │

│  │  │ Kernel        │    │              └─────────────────┘  │

│  │  │ \+rootfs       │    │                                                        │

│  │  │ \+app         │    │                                                         │

│  │  └────────┘    │                                                         │

│  └─────────────┘                                                         │

└──────────────────────────────────────────┘



关键组件：

VMM\(Virtual Machine Monitor\)：firecracker 进程，用 KVM 跑 guest。只模拟 virtio\-net、virtio\-block、virtio\-console、RTC，virtio\-mmio。不模拟 USB/PCI/图形。

jailer：在 VMM 外再套一层沙箱。chroot 到指定目录隔离文件系统、cgroups 限 CPU/内存、seccomp 只放通必要 syscall、drop 所有 capabilities、设 no\_new\_privs。

API server：VMM 启动后开一个 Unix socket，通过 REST API 控制\(配置机器、挂盘、起网、启动\)。控制面用这个 API 编排 microVM。

安全模型：guest 内即使拿到 root，也只能通过 virtio 设备与 host 交互；virtio 后端在 VMM 进程里，VMM 又被 jailer 限制住。要逃逸需同时突破 guest 内核 → virtio → VMM → jailer 四层。



#### **三、选型:Firecracker vs Cloud Hypervisor vs gVisor**

|维度|Firecracker|Cloud Hypervisor|gVisor|
|---|---|---|---|
|隔离|最强\(独立内核\+最小设备\)|强\(独立内核\)|中\(用户态内核，共享 host 内核\)|
|启动速度|\~125ms|\~数百ms|无 VM 启动，进程级|
|bash 兼容性|完整\(guest 是真 Linux\)|完整|多数 OK，部分 syscall 不支持|
|运维复杂度|中\(需自建 rootfs/网络\)|中|低\(OCI runtime，接 docker\)|
|生态/工具|rust\-vmm，但有较多自建|较新|Docker/K8s 直接集成|

推荐 Firecracker 用于企业私有化多用户平台：隔离最强、bash 兼容完整\(用户跑脚本无障碍\)、启动够快。代价是要自建 rootfs 和网络编排，但这部分一次性投入。

若运维团队偏好低复杂度，可退选 gVisor：docker run \-\-runtime=runsc，Agent 装进容器即获得强于普通容器的隔离，但共享 host 内核，极限情况下隔离弱于真 VM。



#### **四、把 Agent 装进 microVM**

##### **4\.1 需要准备的三样东西**

Firecracker 起一个 microVM 需要:

Linux 内核：vmlinux uncompressed kernel\(非 bzImage\)。Firecracker 官方提供参考构建，或用 bzImage → vmlinux 解压。

rootfs:一个磁盘镜像\(ext4 文件\)，内含最小 Linux 用户态 \+ agent 运行时。

配置：通过 API socket 下发 machine/vmlinux/rootfs/network 的配置。



##### **4\.2 制作 rootfs\(内含 Pi\)**

rootfs 是关键：它决定 VM 里有什么。做一个最小化但能跑 Pi 的镜像。

```Bash
1. 创建空镜像(约 300MB 够装 Pi + workspace)
truncate -s 300M rootfs.img
mkfs.ext4 rootfs.img
mkdir mnt
sudo mount rootfs.img mnt

2. 装最小用户态(用 Alpine 或 debootstrap Debian)
sudo debootstrap --variant=minbase bookworm mnt http://deb.debian.org/debian
或 Alpine:见 Alpine rootfs 制作

3. chroot 进去装 Pi 依赖
sudo chroot mnt /bin/bash
在 chroot 内:
apt-get update
apt-get install -y --no-install-recommends ca-certificates curl bash ripgrep git nodejs
装 Node 22(Pi 要求 >=22.19)
curl -fsSL https://deb.nodesource.com/setup_22.x | bash -
apt-get install -y nodejs
装 Pi
npm install -g --ignore-scripts @earendil-works/pi-coding-agent
建运行用户
useradd -m -s /bin/bash pi
mkdir -p /home/pi/.pi/agent/extensions
chown -R pi:pi /home/pi
配置 Pi headless 启动脚本(见 4.3)
cat > /usr/local/bin/pi-start.sh <<'EOF'
#!/bin/bash
set -e
exec su pi -c "cd /workspace && pi server --host 0.0.0.0 --port 8080"
EOF
chmod +x /usr/local/bin/pi-start.sh
exit

4. 卸载
sudo umount mnt
```



要点:

rootfs 里装一份通用 Pi 运行时，所有用户共享这个基础镜像\(只读层\)。

用户的个性化\(skills、mcp\-servers\.json、workspace\)走独立的数据盘，按用户挂载，不进 rootfs。这样 rootfs 可缓存复用，拉起快。

rootfs 以 ext4 装入，启动后可挂为只读；写操作落到数据盘。

注意： 实际上 rootfs 至少需要1G空间，因为 Pi 运行时依赖node环境，加上pi 本身的node依赖库。这里不要为了极致空间而压缩镜像。特别是初期，还需要一些调试工具。可以等后面功能稳定之后，再去除不必要的东西来压缩只读镜像。



##### **4\.3 拉起一个 microVM\(控制面侧\)**

控制面用 Firecracker API 起一个 VM:

```SQL
1. 起 firecracker 进程,开 API socket
socket="/tmp/pi-vm-${user_id}.sock"
rm -f $socket
jailer --id pi-vm-${user_id} \
       --exec-file /usr/bin/firecracker \
       --uid 1000 --gid 1000 \
       --chroot-base-dir /srv/jailer \
       -- $socket &

2. 配置 VM(通过 API)
api="curl -s --unix-socket $socket http://localhost"

机器配置:1 vCPU,512MB
$api -X PUT 'http://localhost/machine-config' \
  -H 'Content-Type: application/json' \
  -d '{"vcpu_count":1,"mem_size_mib":512}'

内核
$api -X PUT 'http://localhost/boot-source' \
  -H 'Content-Type: application/json' \
  -d "{\"kernel_image_path\":\"/srv/vmlinux\",\"boot_args\":\"console=ttyS0 reboot=k panic=1 pci=off nomodules rw ip=user-vm:::ff:eth0\"}"

rootfs(只读基础层)
$api -X PUT 'http://localhost/drives/rootfs' \

$api -X PUT 'http://localhost/network-interfaces/eth0' \
```
