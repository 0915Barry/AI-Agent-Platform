状态定义：

- **排查中**：现象已确认，但尚未定位唯一根因。
- **已修复，待验证**：修复代码已完成，但尚未通过规定的连续或压力验收。
- **已解决**：修复已通过指定验收，且没有出现新的回归。
- **已缓解**：已降低失败概率或影响，但根因仍未彻底消除。

## 2026-11-09：smoke test 成功后重建空 SQLite 数据库

**状态：已解决**

### 故障现象

30 轮验收结束后，`/var/lib/fc/cli-smoke/control-plane.db` 仍存在，但只包含 `runtime_instances`、`runtime_sidecars` 和 `runtime_bindings` 等空运行时表，完整 Control Plane 的业务表不存在。

### 根因

测试主流程成功时已销毁实例并删除整个 `state_root`，但 `EXIT` 清理函数仍无条件调用 `lifecycle destroy`。`RuntimeStore` 在发现数据库已不存在时重新创建了一份空运行库。

### 解决方案

`cli-smoke-test.sh` 的兜底 `lifecycle destroy` 现在只在 `instance_created=true` 时执行。正常成功路径已将该标记设为 `false`，因此不再重建数据库；失败路径仍保留兜底销毁能力。

### 验证情况

修复前空库中的 `runtime_instances`、`runtime_sidecars`、`runtime_bindings` 均为 0，确认它不代表活动资源泄漏。修复后补跑一轮完整 `cli-smoke-test`，启动、对话、Session 落盘、重启续接和销毁均通过；测试结束后 `/var/lib/fc/cli-smoke` 整体不存在，确认空数据库不再被重建。

## 2026-11-09：快速重启后网络租约被旧 watcher 误清理

**状态：已解决（2026-11-09 完成 30 轮连续验证）**

### 故障现象

`cli-smoke-test` 完成首轮对话、Pi 原生 Session 落盘检查、实例重启和上下文续接后，在最终停止实例时报错：

```text
HTTP 500/instance_stop_failed：network lease does not exist
```

故障发生时，Pi 仍能完成第二轮回答，但该实例对应的 SQLite 网络租约已被提前删除。

### 影响范围

影响“停止后立即重启”的同一受管实例。会导致后续 `stop` 失败，并可能使 TAP、nftables 状态与数据库租约记录失去一致性。本问题与 Pi Session 文件内容或 SQLite 历史消息缓存无关。

### 根因

每次启动 Firecracker 后，平台都会派生一个独立生命周期 watcher，用于检测进程意外退出并回收临时网络资源。旧实例显式停止时，旧 watcher 也可能同时观察到 Firecracker 退出。

如果同一逻辑实例很快重启，旧 watcher 在较晚时刻执行清理，就可能根据相同的实例 ID 删除新一代实例刚申请的网络租约。这属于“旧运行代清理新运行代资源”的生命周期竞态。

### 解决方案

修改 `services/instance-manager/lifecycle.py`：

1. 显式停止时，先在 `state_root/stop-intents/<instance_id>` 创建只有 root 可写的停止意图标记，再终止 Firecracker 和清理网络资源。
2. watcher 发现进程退出时，若看到有效的停止意图标记，就等待显式 stop 路径完成，不重复清理。标记最长保护 30 秒，避免 stop 进程意外退出后留下永久残留。
3. watcher 在真正清理前重新读取运行元数据，并同时比对 PID 和 `processStartTicks`。如果状态已不是 `running`，或进程启动标识已改变，旧 watcher 必须直接退出。
4. 新运行代登记时主动删除可能残留的停止意图标记。

### 修复过程中发现的兼容问题

首个方案曾尝试直接向 `runtime_instances.status` 写入 `stopping`。第一轮验收立即发现，现有 SQLite 表约束只允许 `running` 和 `stopped`，因此触发：

```text
sqlite3.IntegrityError: CHECK constraint failed: status IN ('running','stopped')
```

该方案已撤回，改用与数据库状态契约解耦的停止意图标记，不需要扩展或迁移现有状态字段。

### 验证情况

- `lifecycle.py` Python 语法检查通过。
- Instance Manager 现有 24 项单元测试全部通过，其中包含停止意图标记的专项回归测试。
- `cli-smoke-test` 已增加 `pre_session_disk_stop` 和 `final_stop` 失败阶段标识。
- 第一轮验收已确认并排除直接写入 `stopping` 的不兼容方案。
- 修正为停止意图标记后，完成 30 轮无重试连续验收。每轮都通过了创建、冷启动、对话、停止、重启、Session 续接、再次停止、销毁和清理检查，未再出现网络租约丢失。
- 新增独立的 `lifecycle-stress-test` 后，先完成 3 轮探针校验，再完成 100 轮同一实例连续启动与停止压力验收。每轮均验证 Firecracker 进程代数、Sidecar、SQLite 运行记录、网络租约、TAP、nftables、Jailer、API Socket、watcher 和持久化数据盘状态；100 轮结束后没有进程、网络、数据库记录或测试数据盘残留。
- 随后执行异常恢复验收，Control Plane 重启后能够重新接管实例；Firecracker 意外退出后状态得到校准，网络资源完成清理，原数据盘保留并可用于重新启动。

压力验收最终输出：

```text

LIFECYCLE_STRESS_READY cycles=100 slot=0 process_generation=verified lease=verified tap=clean nft=clean watcher=clean volume=destroyed
```

异常恢复验收最终输出：

```text
PASS: Control Plane restart and Firecracker crash recovery preserved instance data
RECOVERY_READY control_plane=reconnected firecracker_crash=reaped state=reconciled network=clean data=preserved restart=verified
```

在单轮异常恢复验收通过后，又增加并完成 30 轮 Firecracker 异常退出压力测试。每轮都直接使用 `SIGKILL` 终止 Firecracker，随后验证 watcher 将 SQLite 状态校准为 `stopped/process_exited`，并清理 Sidecar、网络租约、TAP、nftables、Jailer 和旧 watcher。测试还会对数据盘执行 `e2fsck`，只读挂载并核对预写入的唯一内容标记，然后使用同一数据盘启动下一代实例。

30 轮中每一代 Firecracker 的 PID 与 `processStartTicks` 均不同，网络槽位能够安全复用，数据盘 inode 与内容始终保持一致。异常退出后的资源对账平均约在 `1.2 秒`内完成，最终销毁后没有运行时记录、网络资源或测试数据盘残留。

## 2026-11-09：任务事件流在终态事件前中断

**状态：排查中，已补充现场诊断**

### 故障现象

30 轮连续验收的第 8 轮中，实例启动成功，任务提交和 SSE 请求均返回成功，但 CLI 报错：

```text
任务事件流在返回最终状态前中断
```

Control Plane 日志中没有 `PI_GATEWAY_DISPATCH_ERROR`、Traceback 或明确的 Gateway 错误。该轮在 Session 文件检查之前已失败，因此不能作为 Session 落盘失败样本。

### 影响范围

影响 Control Plane 到 CLI 的任务事件传输链路。当时的清理流程删除了任务记录，无法事后确认任务最后停留在 `queued`、`running`、`completed` 还是 `failed`。

### 处理方案

修改 `scripts/linux/cli-smoke-test.sh`，在聊天传输失败后、自动清理实例之前输出：

- `tasks` 表中的任务状态与错误；
- `task_events` 表中已持久化的事件序列；
- Control Plane 日志；
- Guest 串口日志。

诊断输出以 `FAIL_STAGE=initial_chat_transport` 和 `TASK_DATABASE_DIAGNOSTICS_BEGIN` 为定位标记。

### 当前状态

后续 30 轮严格端到端验收中未再复现。由于首次异常未保留足够的任务状态现场，目前仍不将其归因为 Pi、Gateway、SSE 或缓存故障。新增诊断保留，如后续复现，再以任务表和事件表现场确定中断层级。

## 2026-11-07 至 2026-11-09：Pi 原生 Session 偶发空文件

**状态：已解决（2026-11-09 完成严格 30 轮验收）**

### 故障现象

Pi 能正常返回模型回答，但 microVM 停止后，直接挂载用户数据盘时偶发发现对应的 Pi Session JSONL 文件为 0 字节。

### 影响范围

影响 Pi 原生 Session 的可恢复性。SQLite 历史消息缓存仍可能完整，因此只验证 CLI 历史无法发现该问题。

### 根因

Guest 中 `socat` 的 EXEC 关闭等待时间过短。Host 关闭 TCP 连接后，Pi RPC wrapper 还在等待 Pi 退出、执行收尾和 `sync`，`socat` 就可能提前终止子进程，导致 Session 内容未完整落盘。

### 解决方案

- Guest RPC 入口的 `socat` 改为 `-t 30`，30 秒仅是子进程退出的最长保护时间；Pi 正常提前退出时不会固定等待 30 秒。
- `cli-smoke-test` 删除“失败后重试三次并继续”的宽松逻辑。
- Session 文件缺失、0 字节或缺少 `user/assistant` 消息均立即硬失败。
- 测试直接停止 microVM、离线检查 ext4，并只读挂载数据盘校验原始 JSONL，不允许 SQLite 缓存掩盖原生 Session 问题。

### 验证情况

单轮中已观察到：

```text
PI_NATIVE_SESSION_STORED entries=6 messages=3 roles=system,user,assistant
```

并已验证停止、重启后能从同一 Pi 原生 Session 恢复上下文。基础链路修复后已从第 1 轮重新计数，完成 30 轮无重试端到端验收；每轮的 Session JSONL 均非空，包含 `system`、`user` 和 `assistant` 消息，且重启后均能回复首轮唯一标记。

### 详细记录

完整定位过程、存储链路和上游 Pi 行为见 [`Pi会话异步落盘竞态问题报告.md`](./Pi会话异步落盘竞态问题报告.md)。
