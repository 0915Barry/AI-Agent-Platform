# 一页摘要

## 要做什么

一个**多租户 Agent 平台**:客户在平台上选择工作区,平台为其拉起**独立隔离的运行环境**,
在里面运行 Agent 完成任务;环境可在空闲时自动回收,数据长期保留。

## 已经做到什么

**一条完整的技术链路已经打通并通过实测:**

```
一条命令启动实例 → 环境自动就绪 → Agent 在硬件隔离环境中
完成「调用模型 → 执行工具 → 返回结果」的完整循环 → 空闲自动回收 → 数据保留
```

**六层安全加固全部落地,并有可复现的验收手段:**

| # | 层 | 状态 | 验收方式 |
|---|---|---|---|
| 1 | microVM 硬件级隔离 | ✅ | 实例内核与宿主内核版本不同 |
| 2 | 网络默认拒绝 + 实例间隔离 | ✅ | `iptables` 策略为 `DROP`,放行规则包计数非零 |
| 3 | 实例内降权(Agent 非 root) | ✅ | 覆盖运行时文件返回 `Permission denied` |
| 4 | VMM 进程加固(jailer) | ✅ | 八项自动验收全过 |
| 5 | 凭据外置(实例内零凭据) | ✅ | 实例内凭据检索为空,Agent 仍正常工作 |
| 6 | 实例生命周期(空闲回收) | ✅ | 实测关闭超时实例,数据保留 |

## 还没做什么

| 缺口 | 影响 |
|---|---|
| **镜像构建未脚本化** | 当前镜像为手工构建,**无法从脚本重建** —— 最高优先级 |
| **只读基础层 + 独立数据盘未分离** | 客户数据目前与平台基础层混在同一可写镜像中,**既是隔离问题也是正确性问题** |
| **控制面 API 与前端未开发** | 实例管理仍为命令行脚本驱动 |
| **空闲回收的活动信号精度不足** | 信号只来自网关(模型调用),已实测到一次误判 |

# 二、问题与设计目标

## 2.1 要解决的问题

平台需要具备**在受控环境中执行任意代码**的能力(读写文件、执行命令、安装依赖)。
这带来三个必须解决的问题:

| 问题 | 若不解决的后果 |
|---|---|
| **多租户隔离** | 用户代码与其他租户、与平台基础设施处于同一信任域 |
| **凭据保护** | 模型与工具凭据暴露在执行环境中,等同向用户公开 |
| **环境一致性** | 每台实例手工配置,无法规模化且行为不可复现 |

## 2.2 设计目标(按优先级)

| 优先级 | 目标 | 衡量方式 |
|---|---|---|
| **P0** | 隔离强度达到硬件级 | 每个租户独立内核 |
| **P0** | 凭据不进入执行环境 | 实例内凭据检索结果为空 |
| **P0** | VMM 进程自身受约束 | 八项验收通过 |
| **P1** | 实例可自动化创建与销毁 | 单条命令完成 |
| **P1** | 出站流量可观测、可治理 | 存在唯一必经路径 |
| **P2** | 资源效率支持单机多实例 | 见 §7.3 |

## 2.3 关键约束

| 类型 | 约束 | 带来的影响 |
|---|---|---|
| 部署形态 | 企业私有化,不依赖公有云托管沙箱 | 方案必须可自建于客户 Linux 服务器 |
| 隔离等级 | 容器级隔离不满足安全评审要求 | 排除 Docker / 纯 namespace 方案 |
| **运行时选型** | Pi Agent **不包含内置沙箱** | 官方文档明确:*"Real isolation needs to come from the operating system or a virtualization/container boundary."*<br>**隔离层因此成为必需项,而非增强项** |
| 硬件 | 需硬件虚拟化扩展 | x86_64 与 aarch64 需分别产出构建物 |

## 3.2 三个信任域

| 边界 | 位置 | 跨越方向 | 控制手段 |
|---|---|---|---|

| **开发边界** | 开发脚手架 | 开发工具链 → 目标环境 | **生产环境不存在** |

|---|---|---|---|
| L1 | 开发脚手架 | 提供 KVM 与 Linux 环境 | ✅ |

| L2 | jailer | VMM 进程加固 | ✅ |
| L3 | rootfs | 系统资产与共享运行时 | ✅（只读） |
| L3 | 网络自动配置 | 默认路由与 DNS | ✅ |
| L3 | 运行时身份 | Agent 以普通用户运行 | ✅ |
| L3 | Pi Agent | Agent 运行时 | ✅ |
| L4 | tap + NAT | 连通与隔离 | ✅ |
| L5 | Tool Gateway | 凭据注入、审计、活动记账 | ✅ |
| L6 | 回收器 / 状态端口 | 空闲回收、状态可观测 | ✅ |

# 四、Agent 交互全流程(重点)

> 本章说明:**用户的输入和数据如何到达 Agent,Agent 做了什么,结果如何返回。**

## 4.1 前置:两类数据的路径完全不同

**这是理解整个流程的关键。**

| 数据 | 来源 | 到 Agent 的方式 |
|---|---|---|
| **用户的输入**(指令文本) | 浏览器 | **经网络传输** |
| **用户的文件**(代码、文档) | 数据盘 | **不传输** —— 文件本就在 Agent 可访问的位置 |

> **文件不是"发送给 Agent"的,而是"一直在 Agent 旁边"。**
> **Agent 需要读取时,直接从数据盘读。**

**因此,一次交互的网络流量只有三类:**

1. 用户的指令文本(上行)
2. 模型的请求与响应(经网关到模型)
3. Agent 的输出(下行,流式)

**而文件内容的读写,全部发生在本地数据盘上,不经过网络。**

---

## 4.2 上行:从用户输入到 Agent 收到

```
①  用户在浏览器输入指令，按下回车
        │
        │  WebSocket（连接全程保持，双向流式）
        ▼
②  前端（Web UI）
        │  HTTPS + Token
        ▼
③  后端（控制面）
        │  查询数据库：该工作区运行在哪台计算节点上
        │  内网 HTTPS
        ▼
④  节点代理（计算节点上）
        │  写入 Agent 进程的标准输入（stdin）
        ▼
⑤  ★ Agent 进程（microVM 内）收到指令
```

**Agent 收到的内容只包含指令本身,不包含文件内容:**

```json
{"type":"prompt","text":"把 utils.py 里的 format 函数改成异步的"}
```

---

## 4.3 Agent 的职责:它在流程中做什么

**Agent 收到指令后进入执行循环。它承担八件事:**

| # | Agent 做的事 | 具体内容 |
|---|---|---|
| **1** | **组装上下文** | 把「系统提示 + 工具列表 + 历史消息 + 工具结果 + 新指令」组装成一次模型请求 |
| **2** | **调用模型** | 通过 provider 接口发出请求(经 Tool Gateway) |
| **3** | **解析模型输出** | 判断本次输出是「文本回答」还是「工具调用」,并解析工具名与参数 |
| **4** | **执行工具** | 实际执行 `bash` / `read` / `write` / `edit` |
| **5** | **回灌结果** | 把工具输出追加进上下文,进入下一轮 |
| **6** | **管理上下文长度** | 上下文超限时自动摘要(compaction),保留近期工作 |
| **7** | **持久化会话** | 每一轮写入会话文件(JSONL) |
| **8** | **流式输出** | 模型的增量输出立刻向外转发,不缓冲 |

**Agent 不承担的事 —— 同样重要:**

| 不做 | 由谁负责 |
|---|---|
| 不决定"下一步做什么" | **模型** |
| 不理解代码语义 | **模型** |
| 不生成内容 | **模型** |
| 不判断操作是否安全 | **没有任何组件判断** —— 由 microVM 等外部边界兜住 |
| 不管理多用户 | **平台控制面** |

> **结论:Agent 是「执行者」,不是「决策者」。**
> **它把模型的决定转化为实际动作,再把动作结果反馈给模型。**

---

## 4.4 一次多轮工具调用的完整实例

**任务:「把 utils.py 里的 format 函数改成异步的」**

```
━━━ 第 1 轮 ━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

Agent → 模型：
    指令："把 utils.py 里的 format 函数改成异步的"
    [+ 系统提示 + 工具列表]

模型 → Agent（流式）：
    文本："我先看看这个文件。"
    工具调用：read(path="utils.py")

★ Agent 执行 read
     └─ 从【数据盘】读取 200 行代码

Agent 把结果追加到上下文 → 第 2 轮


━━━ 第 2 轮 ━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

Agent → 模型：
    上下文 + "utils.py 的内容为：<200 行代码>"

模型 → Agent：
    工具调用：edit(path="utils.py",
                   old="def format(x):",
                   new="async def format(x):")

★ Agent 执行 edit
     └─ 修改【数据盘】上的文件

Agent 把结果追加到上下文 → 第 3 轮


━━━ 第 3 轮 ━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

Agent → 模型：
    上下文 + "文件已修改"

模型 → Agent：
    工具调用：bash("python -m pytest tests/")

★ Agent 执行 bash
     └─ 在【microVM 内】实际运行测试

Agent 把结果追加到上下文 → 第 4 轮


━━━ 第 4 轮 ━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

Agent → 模型：
    上下文 + "测试结果：3 passed"

模型 → Agent（纯文本，无工具调用）：
    "改好了，测试也过了。"

★ 循环结束
```

**四轮中的分工:**

| 角色 | 职责 |
|---|---|
| **模型** | 每轮只决定"下一步做什么" |
| **Agent** | 每轮执行那一步,并带回结果 |
| **数据盘** | 文件的读与写发生在这里 |
| **microVM** | 命令实际执行的地方 |

**可观测特征:一次带工具调用的任务,会产生多次模型请求。**
**在 Tool Gateway 的审计日志中可以直接观察到这个次数。**

---

## 4.5 下行:结果的流式返回

```
Agent 的标准输出（JSONL 事件流）
        │
        ▼
节点代理
        │
        ▼
后端
        │  WebSocket
        ▼
前端
        │
        ▼
浏览器逐字显示
```

**Agent 向外输出的是事件流:**

```json
{"type":"text","delta":"改"}
{"type":"text","delta":"好"}
{"type":"text","delta":"了"}
{"type":"tool_call","name":"read","args":{...}}
{"type":"tool_result","name":"read","output":"..."}
{"type":"text","delta":"测"}
{"type":"text","delta":"试"}
...
```

**关键性质:全程流式。**

> Agent 收到模型的第一个增量就立即向外转发,不做缓冲。
> **这也是 Tool Gateway 必须采用流式转发的原因** —— 若其在转发前累积完整响应,
> 用户将长时间看不到任何输出,流式输出的意义完全丧失。

---

## 4.6 数据落点

**一次交互产生的全部数据,去向如下:**

| 数据 | 落点 | 是否离开 microVM |
|---|---|---|
| 用户指令 | 会话文件(数据盘) | ❌ |
| 模型的每次输出 | 会话文件 | ❌ |
| 每次工具调用与结果 | 会话文件 | ❌ |
| **被读取的文件内容** | **发送给模型** | ✅ **是(经网关)** |
| **被修改的文件** | **数据盘** | ❌ |
| 命令产生的副作用 | 数据盘 | ❌ |
| 网关的审计记录 | Lima 上的日志 | —— |

**两条重要结论:**

> **Ⅰ. 文件内容只在"需要被模型读取"时离开 microVM。**
>
> **Ⅱ. 文件的修改全程不经过网络 —— Agent 直接写入数据盘。**

# 五、数据与存储设计

## 5.1 三类存储及其归属

| 类别 | 存什么 | 物理形态 | 生命周期 | 归属 |
|---|---|---|---|---|
| **系统盘(rootfs)** | 操作系统 + 运行时(Node、Agent) | 一个镜像文件,**全平台共享一份** | 长期,随版本更新 | **平台资产** |
| **数据盘** | 用户文件 + 会话记录 | 一个块设备(存储于 Lima 上的一个文件) | **绑定工作区,不随实例销毁** | **用户资产** |
| **控制面数据库** | 工作区、实例、配额的元数据 | 关系型数据库 | 长期 | 平台资产 |

**核心原则:**

> **实例是「计算」,不是「存储」。**
> **实例可抛弃,数据在数据盘里。**

---

## 5.2 「工作区」与「数据盘」的区别

**这两个概念经常被混用,但它们是两个维度的东西:**

| | **工作区** | **数据盘** |
|---|---|---|
| 是什么 | **逻辑对象**(名字 + 索引) | **物理对象**(存储本身) |
| 存在哪 | **控制面数据库**中的一条记录 | **Lima 上的一个文件** |
| 具体内容 | `id=proj-alpha`<br>`volume_path=/srv/fc/volumes/<租户>/proj-alpha.img`<br>`size_gb=10` | 该文件本身,内含用户全部数据 |
| 能否挂载 | ❌ **不能** | ✅ 能 |
| 数量关系 | 一个用户可以有多**个** | 一个工作区对应**一块** |

**两者的关系:**

```
控制面数据库
   │
   │  工作区 proj-alpha
   │    └─ volume_path 指向 ▼
   ▼
Lima
   │
   │  /srv/fc/volumes/<租户>/proj-alpha.img     ← 数据盘（文件）
   ▼
microVM
   │
   │  /dev/vdb                                  ← 数据盘（块设备）
   ▼
   /workspace 与 /home/pi/.pi                   ← 用户看到的位置
```

> **工作区是「名字 + 索引」,数据盘是「东西本身」。工作区指向数据盘。**

**推论:**

| 操作 | 实际动作 |
|---|---|
| 「打开工作区」 | 按记录中的路径找到那块盘,接进新实例 |
| 「删除工作区」 | 删掉数据库记录 **+** 删掉那个文件 |
| 「扩容工作区」 | 扩大那个文件,并让内部文件系统跟上 |

## 5.3 同一个数据盘,在三台机器上分别是什么

**先建立两个基础认知:**

### ① `/dev/vdb` 不是目录,是「块设备文件」

```bash
# 在 microVM 里
$ ls -l /dev/vdb
brw-rw---- 1 root disk 252, 16  /dev/vdb
↑
b = block device（块设备文件）

$ ls -l /workspace
drwxr-xr-x 2 pi pi 4096  /workspace
↑
d = directory（目录）
```

| 路径 | 类型 | 能否 `cd` 进入 |
|---|---|---|
| `/dev` | 目录 | ✅ |
| **`/dev/vdb`** | **块设备文件** | ❌ |
| `/workspace` | 目录 | ✅ |

> **`/dev/vdb` 是「一块硬盘在 microVM 里的名字」,不是一个文件夹。**
> **它必须经过「挂载」才能变成可访问的目录。**

### ② 完整的对应关系

| 在哪台机器 | 系统盘 | 数据盘 |
|---|---|---|
| **Mac / Windows** | 不直接挂载 | 不直接挂载 |
| **Ubuntu KVM 宿主** | `/srv/fc/artifacts/agent-rootfs.ext4` | `/srv/fc/volumes/instances/<实例ID>.ext4` |
| **Ubuntu**（实例 chroot 内） | `.../root/rootfs.ext4` | `.../root/data.ext4` |
| **microVM** | 块设备 `/dev/vda` | 块设备 `/dev/vdb` |

**Ubuntu KVM 宿主上是两个 ext4 镜像文件,microVM 里是两个块设备。**

> ✅ **当前状态**:只读系统盘和每实例独立可写数据盘均已实现并通过真实重启验收。
> 数据盘内的 `workspace/` 与 `pi-state/` 分别绑定到 `/workspace` 和 `/home/pi/.pi`；
> 停止或空闲回收实例不会删除数据，只有显式“销毁”会删除对应数据盘。

## 5.4 数据盘的来源与接入过程

**本节回答两个问题:盘文件本身存放在 Ubuntu KVM 宿主的哪里、怎么产生;以及它是如何被接进 microVM 的。**

> ✅ **当前状态**:数据盘创建、格式化、挂载、重启复用和显式销毁均已实现。
> 当前单机 MVP 以“每实例一块盘”为粒度；升级为多租户后再把路径扩展为
> `/srv/fc/volumes/<租户>/<工作区>.ext4`。

---

### 5.4.1 存放位置

```
Ubuntu KVM 宿主上（当前单机 MVP）：
  /srv/fc/volumes/instances/
       └─ <实例ID>.ext4              ← ★ 数据盘文件的存放位置

多租户目标结构：
  /srv/fc/volumes/<租户>/<工作区>.ext4
```

**选这个位置的理由:**

| 理由 | 说明 |
|---|---|
| **与实例 chroot 处于同一文件系统** | 只有同一文件系统才能使用**硬链接**(跨文件系统不行) |
| **目录划分明确区分两类数据** | `/srv/fc/volumes/` 是**必须保护的**(用户数据);`/srv/jailer/` 是**可随时删除的**(实例状态) |
| **按租户分层** | 便于按租户做容量统计与备份 |

---

### 5.4.2 盘文件的四种来源

| 来源 | 触发时机 | 产生方式 |
|---|---|---|
| **① 新建空盘** | 工作区**第一次**打开 | `truncate` + `mkfs.ext4` + 建立初始目录 |
| **② 从模板复制** | 需要标准目录结构 | 复制一块预制模板盘 |
| **③ 复用已有盘** | 工作区**再次**打开 | **无需任何操作** —— 文件已存在,直接使用 |
| **④ 从备份恢复** | 灾难恢复、版本回滚 | 从对象存储取回 |

#### 「新建空盘」的详细步骤

```bash
# ── 在 Lima 上 ──
IMG=/srv/fc/volumes/tenant-A/proj-alpha.img

# ① 创建 10 GB 的【稀疏文件】
#    仅"声明"容量，不立即占用物理空间
truncate -s 10G "$IMG"

# ② 建立 ext4 文件系统
mkfs.ext4 -q "$IMG"

# ③ 建立初始目录结构 —— 这一步极易被遗漏
mkdir -p /mnt/init
mount -o loop "$IMG" /mnt/init
mkdir -p /mnt/init/workspace /mnt/init/pi-config
chown 1001:1001 /mnt/init/workspace /mnt/init/pi-config     # uid 1001 = pi 用户
umount /mnt/init
```

**⚠️ 第 ③ 步为什么必须做:**

`bind mount` 要求源目录必须存在:

```bash
mount --bind /mnt/data/workspace /workspace
              ↑ 该目录必须存在，否则 mount 失败
```

**因此数据盘内必须预先存在 `workspace/` 与 `pi-config/` 两个目录。**

> 若采用「② 从模板复制」,模板盘内已包含这两个目录,可省去此步。

---

### 5.4.3 从 Lima 到 microVM 的完整过程

```
━━━ 【平台控制面】━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

步骤 1  用户打开工作区
            查数据库取得 volume_path
            确认该实例应落在哪台计算节点


━━━ 【在 Lima 上】━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

步骤 2  准备 chroot 目录
            mkdir -p /srv/jailer/firecracker/pi-01/root

步骤 3  ★ 把两块盘放进「VMM 能看到的位置」
            ln  ~/fc/ubuntu-24.04.ext4                     \
                /srv/jailer/firecracker/pi-01/root/rootfs.ext4

            ln  /srv/fc/volumes/tenant-A/proj-alpha.img    \
                /srv/jailer/firecracker/pi-01/root/userdata.img
            ↑ 硬链接（非复制）—— 同一份数据，两个名字

步骤 4  启动 VMM（由 jailer 包裹）
            jailer --id pi-01 --exec-file firecracker \
                   --uid firecracker --gid firecracker \
                   --chroot-base-dir /srv/jailer    \
                   --cgroup-version 2               \
                   -- --api-sock /firecracker.socket

步骤 5  通过 API 告知 VMM 有哪两块盘
            PUT /drives/rootfs
              {"path_on_host": "/rootfs.ext4",   "is_read_only": true}

            PUT /drives/userdata
              {"path_on_host": "/userdata.img",  "is_read_only": false}
            ↑ 路径是【chroot 内】的路径
              因为 VMM 眼里的 / 就是那个 chroot 目录


━━━ 【VMM 进程内部】━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

步骤 6  VMM 打开这两个文件，建立 virtio-block 后端
            open("/rootfs.ext4",   O_RDONLY)  → fd A
            open("/userdata.img",  O_RDWR)    → fd B
            ↑ VMM 持有的是【文件描述符】
              这也是 firecracker 用户必须对数据盘有读写权限的原因

步骤 7  PUT /actions {"action_type": "InstanceStart"}
            guest 内核启动 → 枚举 virtio 设备
            → 发现两块块设备：/dev/vda、/dev/vdb


━━━ 【在 microVM 内】━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

步骤 8  init 脚本建立访问路径（详见 §5.5）
            mount /dev/vdb /mnt/data
            mount --bind /mnt/data/workspace  /workspace
            mount --bind /mnt/data/pi-config  /home/pi/.pi
```

---

### 5.4.4 关键:为什么步骤 3 必须「放进 chroot」

**这是整条链上容易被忽略、但必须理解的一步。**

```
jailer 用 chroot 约束了 VMM：

    VMM 眼里的 /   =   /srv/jailer/firecracker/pi-01/root/

    因此当 VMM 打开 "/userdata.img" 时，实际打开的是：
    /srv/jailer/firecracker/pi-01/root/userdata.img
```

**若该位置无文件,VMM 将启动失败。**

**把盘「放进去」的三种方式:**

| 方式 | 命令 | 评价 |
|---|---|---|
| **硬链接** | `ln <母文件> <chroot 内路径>` | ✅ **本方案采用** —— 同一份数据,不占额外空间 |
| bind mount | `mount --bind <母文件> <chroot 内路径>` | 🟡 可行,但需在 jailer 的 mount namespace 中验证 |
| ~~复制~~ | ~~`cp`~~ | ❌ **不可用** —— 实例的写入会留在副本中,随实例销毁而丢失 |

## 5.5 实例内部:挂载与 bind

### 前置认知:系统盘与数据盘是两块独立的盘,各自内部有一棵目录树

```
┌─ 系统盘 /dev/vda 内部 ──────┐    ┌─ 数据盘 /dev/vdb 内部 ──────┐
│                             │    │                             │
│  /                          │    │  /                          │
│  ├─ bin/                    │    │  ├─ workspace/              │
│  ├─ etc/                    │    │  │    ├─ main.py            │
│  ├─ usr/local/bin/node      │    │  │    └─ README.md          │
│  ├─ home/pi/   （空）        │    │  └─ pi-config/              │
│  └─ mnt/       （空）        │    │       └─ sessions/          │
│                             │    │                             │
└─────────────────────────────┘    └─────────────────────────────┘

★ 两块盘完全独立。系统盘里【没有任何用户数据】。
```

### 挂载点:一个必须存在的空目录

`mount` 对目标目录有一个硬性要求:**目标必须已经存在**。

```bash
mount --bind  /mnt/data/workspace   /workspace
              ↑ 源目录                ↑ 目标目录：必须已存在，否则 mount 报错
```

因此启动脚本必须先确保它存在:

```bash
mkdir -p /workspace                              # 不存在则创建（空目录）
mount --bind /mnt/data/workspace /workspace
```

> **挂载点 = 一个空目录,唯一作用是「给挂载提供落脚点」。**
> **挂载之后它显示源目录的内容,自己原来的内容(空)被遮蔽。**
>
> **它不是"入口",也不是"系统盘里的用户数据" —— 只是一个空位置。**

### 四个挂载动作

```
①  挂载系统盘
      mount /dev/vda  /
      系统盘内部的目录树成为 microVM 的根

②  挂载数据盘
      mount /dev/vdb  /mnt/data
      数据盘内部的目录树从 /mnt/data 接进来

③  把数据盘中的工作目录接到用户期望的位置
      mkdir -p /workspace
      mount --bind  /mnt/data/workspace  /workspace

④  把数据盘中的 Agent 配置目录接到 Agent 期望的位置
      mkdir -p /home/pi/.pi
      mount --bind  /mnt/data/pi-config  /home/pi/.pi
```

### 挂载完成后的最终视图

**这是一棵「合并」出来的树 —— 它的骨架来自系统盘,部分位置的内容来自数据盘。**
**它描述的是挂载的**结果**,不是任何一块盘的**内部**。**

```
/                             ← 骨架来自【系统盘】
│
├─ bin/  etc/                 ← 内容来自【系统盘】
├─ usr/local/bin/node         ← 内容来自【系统盘】（平台预装的运行时）
│
├─ home/pi/
│    └─ .pi/               ╔══ 这个位置【挂的是】数据盘里的 pi-config/
│                          ╚══ （系统盘上那个同名空目录被遮蔽）
│
├─ workspace/              ╔══ 这个位置【挂的是】数据盘里的 workspace/
│                          ╚══ （系统盘上那个同名空目录被遮蔽）
│
└─ mnt/data/                  ← 数据盘本身的挂载点
     ├─ workspace/
     └─ pi-config/
```

**对照:同一个路径,挂载前后是不同的东西**

| | 系统盘内部的 `/workspace` | 挂载后的 `/workspace` |
|---|---|---|
| 是什么 | **一个空目录** | 用户实际使用的目录 |
| 里面有什么 | 什么都没有 | `main.py`、`README.md`… |
| 内容属于哪块盘 | 系统盘 | **数据盘** |
| 挂载后可见吗 | ❌ 被遮蔽 | —— |
| 它的作用 | 给挂载提供落脚点 | —— |

### ⚠️ 为什么必须挂载一次 + bind 两次

**因为一块数据盘上要放两处内容。**

| 做法 | 结果 |
|---|---|
| 直接把数据盘挂到 `/workspace` | 只能放用户文件,**Agent 的会话记录无处安放** |
| 先挂到 `/mnt/data`,再 bind 出两个子目录 | ✅ 两处内容都在同一块盘上 |

---

## 5.6 `bind mount` 是什么

**它与「硬链接」是同一个思想,区别只在作用对象。**

| | **硬链接** | **bind mount** |
|---|---|---|
| 作用对象 | **文件** | **目录** |
| 效果 | 一个文件有两个路径 | 一个目录有两个路径 |
| 修改一个路径 | 另一个同步变化 | 另一个同步变化 |
| 删除一个路径 | 另一个仍在 | 另一个仍在 |
| 实现方式 | `ln` | `mount --bind` |

**效果示意:**

```
mount --bind /mnt/data/workspace /workspace

     /mnt/data/workspace  ──┐
                            ├──► 同一个目录（同一份数据）
     /workspace           ──┘
```

### 补充性质:bind mount 是「覆盖」

```
bind mount 之前：
    /workspace   ← 系统盘里的一个【空目录】

bind mount 之后：
    /workspace   ← 这个路径指向【数据盘】里的 workspace 目录
    （系统盘里那个空目录仍然存在，但被遮蔽，不可见）
```

**这正是「文件存放在数据盘上,但用户能在 `/workspace` 看到」的实现方式。**

---

## 5.7 数据盘内部的目录结构

**数据盘本身是一个完整的文件系统,内有目录:**

```
数据盘（/dev/vdb）内部
│
├─ workspace/             ← 用户的文件全部在这里
│    ├─ main.py
│    └─ README.md
│
└─ pi-config/             ← Agent 的配置与记录
     ├─ sessions/         ← ★ 对话历史（每轮一个 JSONL 文件）
     ├─ extensions/       ← 扩展 / 插件
     ├─ models.json       ← 模型端点配置
     └─ auth.json         ← 凭据（应保持为空，凭据由网关持有）
```

### ⚠️ `pi-config` 里最重要的是「会话记录」

**很多资料会强调 `pi-config` 里的扩展和插件,但实际上:**

| 内容 | 占比 | 是否必须持久化 |
|---|---|---|
| **`sessions/`（对话历史）** | **大头** | ★ **必须** —— 否则用户下次回来"文件在,但聊天记录没了" |
| `extensions/` | 小 | 视设计而定:平台统一推的放系统盘,用户自装的放这里 |
| `models.json` | 极小 | 平台推送的配置,持久化便于排错 |
| `auth.json` | 极小 | **应保持为空**(凭据在网关侧) |

**因此「把 `~/.pi` 挂到数据盘」的主要理由是会话记录,不是插件。**

---

## 5.8 关键性质:是「接上」,不是「拉入」

**这是整个数据持久化机制的根基。**

```
❌ 拉入（错误理解）

     Lima 上的文件  ──复制──►  microVM 内部
     结果：两份数据。实例销毁时 microVM 那一份消失 → 数据丢失


✅ 接上（实际设计）

     Lima 上的文件  ◄──── 直接读写 ────►  microVM
     结果：只有一份数据，一直存放在 Lima 上，从未被移动
```

**对照:**

| 维度 | 拉入 | **接上** |
|---|---|---|
| 类比 | 把文件拷贝进实例 | 给实例插上一块硬盘 |
| 数据份数 | 2 份 | **1 份,始终在 Lima 上** |
| 实例销毁后 | microVM 那份丢失 | **Lima 那份完好** |
| 更换实例 | 需要重新拷贝 | **直接接上,数据即在** |
| 对数据量的影响 | 拷贝成本随数据量增长 | **与数据量无关,瞬时完成** |

> **microVM 不是「拥有」这块盘,而是「访问」这块盘。盘本体始终在 Lima 上。**

## 5.9 数据盘与实例的生命周期

### 完整时间线

```
━━━ 第一次使用 ━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

①  用户打开工作区 proj-alpha
       控制面查数据库 → 取得 volume_path
       若文件不存在 → 创建一块 10 GB 的空盘

②  启动实例
       系统盘（/dev/vda → /）与数据盘（/dev/vdb → /mnt/data）接上
       bind 出 /workspace 与 /home/pi/.pi

③  用户工作
       所有写入【实时】落到数据盘文件上
       （不存在"关闭时才保存"这一步）

④  空闲超时 → 优雅关闭实例
       sync → poweroff → 进程退出
       ★ 数据盘文件原地不动

━━━ 此刻的状态 ━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

   实例 pi-01                ❌ 已不存在
   proj-alpha.img            ✅ 仍存放在 Lima 的 /srv/fc/volumes/ 下
   数据库记录                 ✅ 保留 volume_path 与 last_used_at

━━━ 第二次使用 ━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

⑤  用户再次打开 proj-alpha
       控制面查数据库 → 同一个 volume_path
       发现文件已存在 → 不新建

⑥  启动【另一台】实例 pi-05
       接上同一块数据盘

⑦  用户看到的内容与上次完全一致
       文件在、对话历史在、他装过的软件也在
```

### 关键结论

| 结论 | 说明 |
|---|---|
| **数据不经过数据库** | 数据库只记录"盘在哪",不存内容 |
| **数据不经过网络** | 用户文件读写在 microVM 本地完成 |
| **不需要"保存"动作** | 写入实时落盘 |
| **恢复不需要"传输"** | 只是重新接上同一块盘,秒级完成 |

### 关机时各层访问路径的命运

```
④  bind mount      → 记录在内存中 → 关机消失
③  bind mount      → 记录在内存中 → 关机消失
②  mount           → 记录在内存中 → 关机消失
①  块设备           → VMM 进程退出 → 设备消失
                                  ↓
                     ★ 数据盘那个【文件】从未被改动
```

**下次启动时四步重做一遍,用户看到的内容不变。**

# 六、六层安全设计

## 6.1 microVM:硬件级隔离

| 要点 | 说明 |
|---|---|
| 硬件虚拟化 | CPU 与内存由 KVM 直接虚拟化 |
| 最小设备模型 | 仅 4 类设备(virtio-net / block / console / RTC),无 USB、无 PCI、无图形 |
| 独立内核 | 每个实例运行自有内核,内核漏洞影响范围限于该实例 |

**验证**:实例内 `uname -r` 与宿主内核版本不同,证明独立内核。

## 6.2 网络:默认拒绝与实例间隔离

| 决策 | 内容 | 理由 |
|---|---|---|
| 网段 | 每实例独立 `/30` | 仅 2 个可用地址,**拓扑层排除邻居关系** |
| 转发策略 | `FORWARD` 默认 `DROP` | 多租户第一原则:默认拒绝,按需放行 |
| 地址分配 | 无 DHCP,由 MAC 反推 | 无状态、无额外服务依赖 |

**规则集:**

```
-A FORWARD -i tap+ -o eth0 -j ACCEPT                                    ← 允许出公网
-A FORWARD -i eth0 -o tap+ -m state --state RELATED,ESTABLISHED -j ACCEPT ← 允许回包
-P FORWARD DROP                                                          ← 其余丢弃
```

**两个关键性质:**

- **到 Lima 的流量走 `INPUT`,不走 `FORWARD`** —— 因此把 `FORWARD` 全部关死,模型调用仍可用。这是后续 air-gap 的技术基础。
- **隔离依赖"没有允许规则",而非某条禁止规则** —— 新增网段或设备自动被挡住。

## 6.3 身份:实例内降权

| 主体 | uid | 权限范围 |
|---|---|---|
| `root` | 0 | 系统资产与系统配置 |
| **`pi`(Agent)** | **1001** | **仅 `/workspace` 与 `/home/pi`** |

**验证结果:**

| 操作 | root | pi |
|---|---|---|
| 读 `/etc/shadow` | 成功 | `Permission denied` |
| 写 `/usr/local` | 成功 | `Permission denied` |
| **覆盖运行时文件** | 成功 | **`Permission denied`** |

**已修复的构建缺陷**:解压运行时发行包时保留了包内的 `uid/gid`,而创建用户时会分配到同一 uid,
**使低权限用户成为运行时的所有者** —— 反而打开了要防御的路径。
修复方式:解压后显式将运行时目录属主收敛为 `root`。

## 6.4 VMM 加固:jailer

**jailer 按序执行的关键动作:**

| 分组 | 动作 | 作用 |
|---|---|---|
| 清场 | 关闭继承的 fd;**清空环境变量** | 防止父进程的 fd 与凭据泄漏 |
| 建笼 | VMM 二进制复制到 chroot;`pivot_root` + `chroot` | 根目录被替换为仅 8 个条目的目录 |
| 建笼 | `mknod` 创建 `/dev/kvm`、`/dev/net/tun` | **仅放行这两个设备** |
| 上锁 | `setrlimit` | 限制文件描述符数 |
| 交钥匙 | **降权到指定 uid/gid 后 exec VMM** | ★ 核心动作 |

**组件归属澄清**:seccomp 由 **Firecracker 自身**提供(默认开启),**不是 jailer 的职责**;
且按线程延迟加载(API 线程在服务启动时,VMM/VCPU 线程在执行实例代码前)。

**验收结果(八项):**

| 检查 | 结果 |
|---|---|
| 运行用户 / 属组 | `firecracker` |
| chroot 可见条目 | 8 项,无 `/etc`、`/bin`、`/usr`、`/home` |
| seccomp(全部线程) | `Seccomp=2` |
| capabilities | `CapEff=0`、`CapPrm=0` |
| 环境变量条数 | 0 |
| 文件描述符上限 | 2048 |

## 6.5 治理:凭据外置

**设计意图:将「持有凭据」与「使用凭据」解耦。**

```
实例（持有占位串）── 内网明文 ──► 网关 ── HTTPS + 真实凭据 ──► 模型服务
                                    ▲
                          真实凭据仅存在于此
```

| 要点 | 实现 |
|---|---|
| 监听范围 | 仅绑定内网侧地址,**不绑定 `0.0.0.0`** |
| 凭据存储 | Lima 上的文件,权限 `600`,不进入实例、不写入日志 |
| 凭据注入 | 剥离入站凭据,注入平台凭据 |
| 响应模式 | **流式转发**,不缓冲 |
| 审计 | 记录方法 / 路径 / 状态码,**不记录任何请求头** |
| 代理 | **显式禁用**环境代理,避免被失效代理劫持 |
| 活动记账 | 每次请求后刷新活动时间戳(供回收器使用) |

**该层的战略价值**:引入后,以下能力均可在同一位置增量实现,无需架构变更 ——
租户鉴权、配额限流、计量计费、多供应商路由、密钥轮换。

## 6.6 生命周期:空闲回收

**设计意图**:实例只要运行,实例内存就持续占用。
不回收,单机容量将由「注册用户数」而非「并发活跃数」决定。

| 组件 | 职责 |
|---|---|
| 回收器 | 扫描 / 常驻监控,超阈值执行优雅关闭 |
| 活动标记 | 刷新活动时间、标记长任务、列出空闲情况 |
| 状态端口 | HTTP 状态查询(快照 / JSON / 实时流) |

**优雅关闭顺序(硬要求):**

```
① 通知实例优雅退出
② sync —— 把内存中的写刷到磁盘
③ 等待进程退出 → SIGTERM → SIGKILL
④ 保留 chroot（数据盘是母文件的硬链接，数据不丢）
```

**状态目录:**

```
/var/lib/fc/
  ├── instances/<id>.json     实例元数据
  ├── instances/<id>.busy     存在 = 有长任务，回收器跳过
  └── activity/<实例IP>     mtime = 最后活动时间
```

**已知精度缺口**:活动信号当前仅来自网关(模型请求),
用户"在界面上翻阅"或"在终端排查"时不会产生模型请求 → **已实测到一次误判**。
根治方向:活动信号改由「平台 ↔ Agent 的 RPC 通道」提供。

# 九、关键架构决策

| ID | 决策 | 备选方案 | 结论与理由 |
|---|---|---|---|
| **ADR-01** | 采用 **microVM** 作为隔离单元 | 容器;普通 VM | **采纳**。容器共享内核,不满足安全评审;普通 VM 开销与密度不可接受 |
| **ADR-02** | 采用 **Firecracker** 而非 QEMU | QEMU;Cloud Hypervisor;gVisor | **采纳**。设备模型最小,攻击面最小,密度最高。**若后续需 GPU / PCI 直通,可评估 Cloud Hypervisor** |
| **ADR-03** | Agent 运行时**部署于实例内部** | 远程服务化 | **采纳**。远程调用无法提供"在用户自有隔离环境内执行"的语义,且会使平台接触全部用户数据 |
| **ADR-04** | 凭据**置于实例边界之外** | 凭据写入实例 | **采纳**。后者在多租户下等同公开凭据 |
| **ADR-05** | 运行时资产属主 root,Agent 以普通用户运行 | 全部以 root 运行 | **采纳**。后者使单次注入导致运行时被持久化污染 |
| **ADR-06** | 网络转发**默认拒绝** | 默认放行 | **采纳**。默认放行会使新增实例自动获得互访能力 |
| **ADR-07** | 每实例**独立 `/30` 网段** | 共享大网段 + 防火墙 | **采纳**。在拓扑层排除邻居关系,降低对规则正确性的依赖 |
| **ADR-08** | 活动信号取自网关 | 进程 CPU 占用 | **采纳但已知不足**。CPU 会误判长任务与阅读中的用户;正解是会话层信号 |
